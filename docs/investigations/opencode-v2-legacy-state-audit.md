# OpenCode V2 migration: legacy-state dependency and incident audit

Date: 28 October 2026. Audited revision: `25b51b94470f94f0002325271c4d93df89ab0697`, branch `codex/johannes-assistant`, based on `codex/opencode-v2-migration`. Assistant PR #312 inherits migration PR #349.

## Result

The migration does **not** currently pass the user's deletion criterion: remove the old engine configuration and registry dependencies after migration, then continue operating normally with native V2 state and zero legacy adapters.

The old configuration database is still a normal-runtime source of truth. Settings reads, edits, permission checks, provider discovery, connector installation and startup regeneration still use it. Removing it can silently reset policy preferences and remove capabilities. Old chat history is also still consulted during normal chat reads and unfinished Undo recovery.

This does **not** mean project tasks have two databases. Project tasks remain in the app's `runtime.sqlite`; native OpenCode has its separate conversation/execution database. The app database also contains legitimate app records that V2 is not responsible for storing. The dangerous duplication is engine configuration across the old DB and generated settings/admission files. A complete migration must retire legacy engine state while preserving app-owned records.

### Deliverables and scope

- This report documents confirmed incidents, source-level deletion consequences, migration history and acceptance criteria.
- [Reference inventory](opencode-v2-legacy-state-references.csv): 485 classified source references across 71 tracked production files, including definitions, imports, callers and comments. These are not 485 independent bugs. The appendix groups every inventoried file and line.
- Additional paths for live app records and fallback files are listed below.
- Scope: tracked TypeScript, TSX, JavaScript and MJS in `apps/` and `packages/`, relevant tests/history, and read-only inspection of the running dev profile. Test support, generated source, build output and scripts are excluded from the production reference inventory.
- Symbol/path searches were followed through central stores, direct consumers, entrypoints and relevant routes. An unexecuted branch or arbitrary external plugin cannot be certified safe by static analysis; no such certification is claimed.
- No application implementation, real profile data, queued messages or permissions were changed. The only executions were read-only inspection and an isolated synthetic-store probe. No production migration/deletion experiment was performed.

### How the migration introduced it

- Commit `98e0bfbedb34e77acfd60ce0be5abb75e15d5d77`, 26 October 2026, introduced native project admission and the generated registry/settings dependency. The older registration function continued to persist only app state.
- Commit `5c110b4fd9ff7c299f297549a85e7d0e2f3403e1`, 27 October, introduced shared managed engine configuration and made registration sufficient for managed-mode readiness. It did not connect registration to generated configuration publication.
- The regression is a new runtime dependency whose lifecycle was not integrated with existing project creation.
- Assistant merge/rebase commits inherited this behavior. The user did not cause it by choosing “All projects.”

The released-engine test [apps/server/src/managed-config.released.test.ts:19](https://github.com/eigenweltlabs/legalwork/blob/25b51b94470f94f0002325271c4d93df89ab0697/apps/server/src/managed-config.released.test.ts#L19) defines its projects before configuration generation and startup. Creating chats in those projects does not test creating a new project after startup. Assistant route tests mock the engine and do not exercise the real admission plugin.

## 3. Why Run and Dictate flash

Tracked in [LW-290](https://linear.eigenweltlabs.com/dashboard/workspace/wv2xFg1Q86nVH3QeIaHwqKWlZy09cRjY/project/linear-project-19ca5118-e9b9-4812-bdda-bf0007ccec8a/task/sfkkydrjpm8edpkql57i6rrk).

| Background fetch | Transition state | Composer consequence |
|---|---|---|
| false | idle | Usable |
| true | switching | Disabled/dimmed |
| false | idle | Usable again |

There is no actual navigation. This explains why a background refresh can visibly flash the controls.

### What establishes the two-second cadence?

- The Assistant retry loop is exactly2000ms and is confirmed in the engine logs.
- Native terminal events invalidate the tracked snapshot at [apps/app/src/react-app/domains/session/sync/session-sync.ts:1496](https://github.com/eigenweltlabs/legalwork/blob/25b51b94470f94f0002325271c4d93df89ab0697/apps/app/src/react-app/domains/session/sync/session-sync.ts#L1496). Reconnect and other event paths also invalidate snapshots.
- The UI also polls native status every2000ms at [apps/app/src/react-app/domains/session/surface/session-surface.tsx:848](https://github.com/eigenweltlabs/legalwork/blob/25b51b94470f94f0002325271c4d93df89ab0697/apps/app/src/react-app/domains/session/surface/session-surface.tsx#L848). That status query alone is separate from the snapshot query and is not proof of the direct trigger.
- The state/disable mechanism is reproduced. A synchronized renderer/SSE trace proving which invalidation caused every observed flash was not captured. That trace is part of the ticket's validation requirement.
- Git history attributes the transition controller to `849f7511` on 26 June, before this migration. The migration did not introduce that exact line. The current rejection/retry loop can expose or amplify the existing UI defect.

Do not “fix” the flash by suppressing legitimate synchronization. A usable same-chat snapshot must remain interactive during background refresh; real navigation and concrete send constraints must still work.
