# Synthetic mail benchmark checkpoints

EIG-141's Windows baseline exceeded its 300-minute step limit before indexing finished. No final baseline report or reusable corpus was exported. Its retained progress logs do not qualify 100,000-message performance. That failed runner's database is unavailable; this tooling cannot recover it retrospectively.

The benchmark can now retain generator-verified input after a bounded failure. This does not start a benchmark automatically. A new full baseline still needs the owner's authorization and the agreed build/fix sequencing.

## Bounded execution

For an authorized run, configure both environment variables before invoking the existing benchmark command:

- `LEGALWORK_MAIL_BENCH_BUDGET_MS`: positive integer milliseconds, at most one day. This bounds the measurement worker's lifetime.
- `LEGALWORK_MAIL_BENCH_CHECKPOINT_DIR`: a new artifact directory outside the generated profile.

The driver retains its private synthetic profile and source-content fingerprint. Budget expiry stops the worker process family and waits for actual process exit before attempting a checkpoint. A failed or timed-out measurement still exits unsuccessfully. Without these variables, no new deadline or automatic checkpoint export is enabled.

Foreground IPC sampling starts after the worker registers its read handler. This prevents a ping sent during database setup from remaining unanswered and suppressing later observations. Historical reports are preserved; they do not gain measurements from this change.

Choose a worker budget shorter than the CI step deadline. Compilation, verifying every original, copying the database and artifact upload need additional time. An external hard kill can prevent retention entirely.

## Manual checkpoint export

After stopping every process using a generated profile:

```sh
node apps/server/scripts/mail-benchmark.mjs --checkpoint /absolute/synthetic-profile /absolute/new-checkpoint-directory
```

Use only a profile generated by this benchmark, never a real mail profile. The exporter requires the three expected synthetic accounts, no credential/OAuth rows and the complete original inventory. Every original is read through the hash-verifying content store and compared with the deterministic generator. A partial original inventory or altered original rejects export.

Measurement and export commands reject an existing output before compilation or worker startup. Reports also use exclusive creation, preserving earlier measurements if a destination appears during the run.

The source uses the existing offline maintenance fence: DELETE journal mode and an exclusive transaction prevent a concurrent writer during verification/copy. A live WAL connection rejects capture. The copied database stays encrypted; streamed file hashes verify the copy, and only the database plus an explicit metadata allowlist are exported. Existing output is never replaced.

## Evidence contract

Checkpoint metadata uses kind `legalwork-synthetic-benchmark-checkpoint`, `measurementState: incomplete`, `report: null`, the actual message count, coverage and database/corpus hashes. Tiny native fixtures are labeled with their real count. Calls without a source fingerprint retain a null value.

No baseline JSON is fabricated. Existing retained-performance and full-app measurement consumers reject the checkpoint kind. Resuming unfinished extraction/indexing and obtaining qualified measurements remain separate work. The ordinary `--export` path still requires 100,000 messages, a completed baseline report and a complete clean index; a completed measurement does not itself establish that latency targets passed.

For hosted retention, upload only `mail.sqlite` and `benchmark-profile.json` from the verified checkpoint directory, even when the measurement step fails. Retain these synthetic artifacts briefly, including the explicitly disposable test key. Never archive the whole generated profile or a user runtime directory.

Validation uses actual Node/encrypted SQLite with 100-message synthetic fixtures, process-exit and process-family termination tests. It does not run a new 100,000-message baseline or change runtime durability settings.

The Windows checkpoint job also enables `LEGALWORK_MAIL_BENCH_CHECKPOINT_SMOKE=1` for an actual 100-message driver failure-path test. It creates a report collision after startup, then checks the unsuccessful exit, preserved report and verified incomplete checkpoint. The same opt-in test can run through `node apps/server/scripts/mail-acceptance.mjs --suite testing/benchmark-export`; ordinary provider certification excludes this tooling suite.
