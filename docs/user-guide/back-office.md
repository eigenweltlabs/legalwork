# Back Office

Open **Back Office** from the global sidebar. Choose **Matters**, **Clients** (German: **Mandanten**), **People** or **Organisations**. **Create** opens an editable record panel. Enter its name and press Enter or leave the field to save. Click a grid cell to edit it. Relation pickers connect existing records. Changes to views stay inside the current screen. Back Office follows the app’s appearance setting, including Dark, Blackout and System. Tables, menus, record panels and dialogs use the same theme.

Searchable pickers show plain option names and a checkmark beside selected rows. For fields that allow several values, select the rows you want, then choose **Apply**.

Use **Filter**, **Sort** and **Options** to control the table. Drag column headers to reorder them and drag their borders to resize them. Open the view selector, such as **All Matters**, then **Add view**. Name the view and choose **Table**, **Kanban**, **Calendar** or **List**. Kanban requires a select or single-relation field for its stages. Calendar uses a date field and supports day, week and month. Saved views keep their layout, columns, search, filters and sort. Switch views in the selector without reloading the page. A saved view’s options allow editing its name and configuration or deleting it. Deleting a view keeps its records. Use **Options > Save** to update the selected view’s current filters and columns, or **Add view** to save another view. Search is available in **Options > Search records**. **Options > Show archive** displays archived records. Open a record's **Record options > Restore record** to restore it.

Kanban cards can be dragged to another stage, which updates the grouping field. Calendar cards can be dragged to another date, which updates the selected date field. Use a calendar day’s plus button to create a dated record. Creation and update timestamps are read-only. Cards and list rows open the same record panel and use the same field editors as Table.

Connect records through a project's metadata. Open **Project Home > Configure fields**, add a field and choose a Back Office object as its type. Built-in and custom objects are available. Save the definition, then select records in the metadata row on Project Home using the same searchable picker as the table. Field settings do not select records. Click a selected name to open its Back Office record. Several projects can select the same record. Removing a metadata value keeps the record. Internal relationship tables do not appear as directory objects. The separate matter/project linking panel is no longer used.

**Organisations** includes companies, courts, public authorities, law firms, associations and other institutions. Use **Organisation type** to distinguish them. Clients, people and matter parties can refer to an organisation.

Open **Data model** to manage visible objects and fields. Choose an object, then **New field > select a type** to configure a custom field. Protected fields retain the types and relationships LegalWork needs. Labels remain editable. Changes affecting existing records show a review before applying. Changes that would invalidate stored values remain blocked. **Settings** edits the object's names. Custom objects can be archived and restored. **Add object** creates another directory type with a required Name field.

### People and types

People includes internal team members and external contacts in one directory. **Type** is a normal select field: Partner, Counsel, Associate, Assistant, Operations, Freelancer, Other team member and External contact are starting options. A model editor can open **Data model > People > Type**, edit **Options, separated by commas**, and save additional types. The assistant can also update the model. Types are not tied to employee status or app permissions.

New people start with **Active** enabled and Type set to External contact when that option exists. Choose the actual type explicitly. Existing people keep their existing details and assignments; the upgrade enables Active without guessing their type. Set Active to false when someone should stop appearing in new active-team assignments. Existing project links remain readable.

### File fields

Fee agreements have **Signed agreement**, and invoices have **Invoice PDF**. For another attachment field, open **Data model > choose an object > New field > File**. Enable **Allow several files** for up to 20 attachments in a custom field. Each file can be up to 10 MB.

Click a file field and choose **Attach a copy**, or **Choose from a project** to browse an existing project file. This creates an immutable copy with its own identity. Its access follows the Back Office record and field; the original file and its project permissions stay unchanged. Uploading a replacement creates a new version identity. Click the filename to preview the attached version in the document viewer, or choose **Download**. The preview is read only. Removing an attachment from a field does not delete the original project file.

Files work locally without a platform update or team sync. With firm sharing enabled, the verified attachment bytes are uploaded before the record references them. Other authorized computers download and cache the same version when it is opened. Financial and private fields keep their existing restrictions. CSV export includes attachment names; CSV import does not upload or recreate files. Full document-management workflows remain separate.

Use **More actions > Import CSV** to map columns and preview rows, warnings and errors before applying the batch. Map **Source ID (optional)** when your CSV has stable identifiers from a previous system. These are import metadata, not fields in your data model. Matching source IDs update existing records. A matching name alone keeps records separate. Relation columns accept an accessible record ID or `source:source-ID`, with `|` separating several references. Duplicate source IDs and unavailable relations are rejected. **Export CSV** includes only records and fields you may read.

Back Office opens one directory automatically. When a platform administrator enables Back Office sync, it uses the firm workspace and syncs subsequent edits automatically. With sync disabled it uses local records. Sync errors appear only when they need attention. Use **More actions > changes pending** to review queued edits. Existing local records are preserved for a one-time migration when enabling sharing. Shared project links require the project to be shared with that firm. Project permissions remain independent of matter links. Administrator permissions separately control editing records, customizing the data model, and access to billing data such as rates, time entries and invoices.

Offline record edits remain queued. Model changes require an online connection. Sync errors appear above the current view. Open **More actions > changes pending** to compare your edits with the team version. **Apply my changes** reapplies the reviewed fields to the latest team record. If that record changes again, review it again. **Discard queued edit** removes that record's queued edits and reloads the team version after confirmation. If access is revoked, the managed replica is cleared while queued edits remain available for resolution. Signing out warns about pending changes.

The starter model includes fee agreements, time entries, billing items and invoices under **More** as data foundations. Currency amounts are kept separate by currency. A matter's value in dispute describes the case value. Private work notes, client-facing narratives and financial fields have separate access rules. Stopwatch, timesheet review and invoice issuance are later workflows.

### History and verification

Open a saved record and choose **History** beside **Home**. Entries show who made each change, when it was recorded, and the previous and new values using the field definitions from that time. **Load earlier entries** shows older revisions. **Entry details** shows the model version, identity source and proof fingerprint. Archived records keep their history; use **Options > Show archive** to open one.

Click an attachment filename in **History** to download the version from that revision, including a version removed from the current record. Your current and historical access rights still apply. Removing a file reference does not overwrite its earlier bytes.

History and exports apply both historical and current access rules. Model administration does not grant access to financial fields or somebody else's private notes. Restricted related matters and projects stay restricted. Some original details may therefore be hidden. A record's history is unavailable after its access is revoked. A dated baseline identifies existing data captured when this history system was enabled; it does not claim that earlier activity was verified when it occurred.

Choose **Export history** to download signed JSON containing the authorized selection, proof chains and the number of original payloads withheld. It includes previous values that you are authorized to read. Keep the JSON unchanged for verification. It is a history selection, not a complete database backup, and does not include attachment bytes. The assistant can inspect record, model and saved-view history, export a selection, or verify an existing export separately from the current Back Office history.

**Verification** explains where signatures were checked and whether an independent checkpoint has been acknowledged. Signatures make changed entries detectable. Separately retained, trusted checkpoints also help detect a restored older copy. Verifying an export against checkpoints copied from that same export establishes consistency, without independent rollback evidence. Retain Back Office history exports and trusted checkpoints separately according to your firm's evidence-retention process. This protects Back Office changes, not other app activity. Local verification cannot independently detect replacing the whole computer's database, keys and checkpoints together.

Local record history works without team sync or a platform connection. Shared history shows accepted team changes, uses current platform permissions and requires a supporting platform version and a connection. Pending edits remain in **More actions > changes pending** until accepted. An older or unreachable platform does not cause LegalWork to substitute cached team history for an authorization check.

If your firm removes record or field access, LegalWork clears those copied values from its managed record and history cache. The firm history is checked with your current permissions. Queued edits keep the fields you actually changed, with inaccessible fields removed and affected drafts held for review. A disconnected team directory retains only the remaining plain authored fields for review; copied file/relationship details and privileged values are removed from those proposals. Reconnect with permission before sending them.

Queued drafts belong to the account and platform that created them. Switching accounts clears managed team records and history from the previous connection. The remaining plain fields you authored stay held for review, and another account cannot send or discard them. Sign back in with the same account on the same platform, open **Back Office > More actions > changes pending**, and compare them before choosing **Apply my changes** or **Discard queued edit**. Drafts from older builds without a recorded author are preserved outside the automatic sync queue. An administrator must investigate and manually re-enter authorized changes; the app does not assign these old drafts to a new account.
