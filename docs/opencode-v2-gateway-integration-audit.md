## Native v2 changes the architecture decision

Pinned `packages/core/src/mcp/oauth.ts` now deduplicates rotating refresh requests **across the native process** by endpoint/client/refresh-token (lines31–53). Credential invalidation checks the stored refresh token still matches the one presented before deleting it (lines267–314). A single released v2 engine therefore already addresses the central old multi-location refresh race at source level. Its MCP lifecycle also has per-server locks and conditional live-connection callbacks. The gateway is not necessary merely because v1 had that race, and no real 2.1.4 refresh-race fixture has yet been run in this audit.

The remaining gateway value is an ownership choice: LegalWork's encrypted shared vault, isolation of provider credentials from the engine, one owner shared with non-agent LegalMemory calls, durable cross-profile handover, and the previously reviewed recovery UI. Native OAuth offers a smaller engine-owned path and its existing integration/forms API, but does not by itself establish those same LegalWork vault/handover contracts. **Decide this ownership boundary explicitly before integrating the adapter**. If retaining the previously approved server-owned connector design, reuse its core and remove the old v1 glue. If choosing native ownership instead, retain the gateway evidence/fixtures as acceptance criteria and design a safe credential transition; do not run both OAuth owners for one connection.

## Recommendation

My conditional recommendation is to retain the user's already approved LegalWork-owned connector boundary and reuse its credential, refresh, handover and protocol implementation, provided the user confirms that boundary after seeing the native refresh improvement. Adapt its engine and renderer wiring to released OpenCode 2.1.4. Keep one native engine, the shared capability library, native first-party LegalWork tools and MCP for external connectors. A gateway does not require an embedded SDK or a second engine.

The current gateway code already provides useful behavior:

- The existing shared registry remains authoritative; explicit project overrides have distinct connection identities. The existing encrypted `OAuthVault` is reused, including built-in connector entries. A separate short SQLite transaction admits one MCP manager per credential store across processes.
- OAuth discovery, PKCE/state/issuer validation, client registration, token rotation and refresh live in LegalWork. The engine gets only a connection/project-scoped process-local gateway bearer and `oauth:false`. Provider access/refresh/client secrets stay out of engine configuration; management capability and gateway capability are distinct.
- Per-connection refresh queues re-read current tokens and reuse a replacement. Ordinary tool calls and unrelated connections remain parallel. Logout retires a generation and cancels work before clearing credentials; stale callbacks cannot resurrect it. Only explicit HTTP401 triggers one authenticated retry. Network failures, ambiguous execution and MCP tool errors are not replayed. HTTP403 scope escalation preserves the old grant and requests explicit consent.
- Saved sign-ins transfer through a staged encrypted destination and recovery journal before the old entry is retired. Cross-profile ownership, ambiguous accounts and interrupted writes fail safely. Recovery UI retains Retry transfer / Sign in again and reports real blockers.
- The modern protocol forwards full requests and streaming responses, metadata, resources, prompts, interactive continuations, Tasks requests and catalog notifications. Legacy sessions bridge only the capabilities their client actually declares. Workspace-specific request context, cancellation and progress remain isolated. Header handling strips the local gateway bearer/cookies and decoded compression headers. There is no discovered tool-output truncation or schema-count cap in these forwarding modules.

## Required adaptation and sequence

1. **Establish a source checkpoint.** Reconcile the gateway branch with dev, including its final independent-review fixes. Port only gateway-related changes into this already-modified v2 worktree; do not overwrite native client, browser, plugin packaging or typed-config changes wholesale. Preserve the existing vault and durable handover records; never create a second token owner.
2. **Port the server core first.** Reuse `mcp-manager-store.ts`, `mcp-manager.ts`, `mcp-migration.ts`, `mcp-process-ownership.ts`, `mcp-gateway.ts`, OAuth callback issuer propagation and recovery tests. Resolve shared config/vault/firm lifecycle hooks explicitly. Keep manager startup/credential handover before engine activation and strip vault-key material from managed child environments.
3. **Replace the v1 engine glue.** The gateway branch's `LegalWorkMcpGateway(input.directory).config(config.mcp)` and `/mcp` proxy interception are v1-specific. Derive gateway descriptors server-side before the new typed MCP definitions read, convert them to native `mcp.servers`, and let the existing native MCP loader consume them with the canonical project trust guard. The earlier async mcp.transform callback was invalid because transforms are synchronous; the corrected synchronous private-registry guard has passed a released-engine 12-assertion no-spawn test with the builtin loader enabled. Root independent verification is pending. No separate MCP executor or replacement configuration loader is justified by that invalid async callback. Do not add a second renderer `mcp.add` write or put provider credentials back in native config.
4. **Use one OAuth owner per connector.** Gateway-managed remote servers must use LegalWork's manager OAuth/recovery API and callback state/issuer. Their native loopback entry has OAuth disabled. Preserve native integration/MCP APIs for connectors outside manager ownership. Port UI status carefully: gateway `connecting`/migration-blocked states are distinct from native `pending`; neither should trigger a second login or hide recovery controls.
5. **Prove actual native capabilities.** Native 2.1.4 source has MCP elicitation-to-Forms handling, including URL forms, and an explicit legacy roots handler. Its advertised capabilities do not include sampling in the inspected client. Verify the real engine through the gateway for form replies/conditions, OAuth state+issuer, permissions, full rich/structured tool results, changing catalogs, timeouts, progress, cancellation and two project identities. Gateway SDK tests that advertise sampling/Tasks do not prove the engine implements them. Preserve native CodeMode negotiation headers: modern forwarding already retains all MCP-prefixed headers. Keep unsupported negotiated features explicit rather than synthesize capabilities.
6. **Re-run credential migration and packaging.** Use real v1 sign-in → immutable test profile → manager transfer → one released v2 engine/two project locations, including simultaneous expiry, restart, interrupted activation, disable/enable, logout during refresh, malformed/ambiguous grants and Firm Hub revocation. Verify private runtime capabilities cannot call management endpoints or cross projects. Repeat packaged Node dependency graph and macOS/Linux/Windows coverage; old two-engine v1 tests cannot establish v2 parity.
7. **Measure cost and latency without changing signal.** The gateway removes duplicate refresh ownership, not model context. Tool schemas/results still reach the native engine. Benchmark schema bytes, cache usage, model tokens and the extra loopback latency separately; preserve all outputs and native parallel tool behavior. Use catalog invalidation rather than per-token polling. No automatic context compression or claimed token saving is justified by this branch alone.
