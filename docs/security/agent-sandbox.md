# Protected command execution

Agent command sandboxing is **off by default**, including existing installations that only saved a network choice. Settings > Tool Permissions controls the application default. The icon-only shield floats in the top-right corner of each chat surface without adding a row or shifting messages. It opens a menu offering **Use application default**, **Sandbox off**, or **Sandbox on**, with its own network choice when on. An explicit chat override is independent of later application changes. Child agents inherit their parent chat's effective settings. Removing an override restores inheritance.

Off runs commands directly on the host (Bash on macOS/Linux, PowerShell on Windows), with the computer's installed tools and OS access. It creates no VM and does not apply sandbox folder or network restrictions. Shell, read, edit, external-folder and network tool permissions are still evaluated conservatively for the whole command; they are approvals, not an OS confinement boundary. Read-only workers refuse native execution. Native processes have bounded output and timeouts; Unix process groups and Windows kill-on-close jobs reap background descendants.

On uses isolated command environments inside a shared Linux VM. The desktop includes QEMU 11.1.2, the Linux kernel, Python, Node, and the guest supervisor. Users do not install Docker, WSL, Homebrew, MSYS2, or a Python runtime for protected commands. Missing or damaged resources block protected execution, with no host fallback. The structured calculation tool remains a separate, always-isolated, offline evaluator; its internal runtime is not the agent shell setting.

Only the host credential can change application or chat sandbox settings. The agent's client/owner bearer token cannot. Changes cancel affected commands and await cleanup before returning; unrelated explicit chat overrides keep running. The managed engine always routes shell commands through LegalWork, allowing protected and native chats side by side without restoring an engine-level bypass. An externally managed engine retains its own execution policy.

### Application default sync

Signed-in accounts with the `settings_presets` entitlement (Sync, Plus, Pro) sync the application default via `GET/PUT /api/desktop/settings`. Chat overrides stay local. The model API stores one default per organization/member and checks current membership and plan access. An empty account starts off. Polls run on startup and every 30 seconds; local edits also trigger a round. Local changes take effect immediately, remain saved offline, and retry later. A stale revision cannot overwrite another device's newer setting; the newer value is applied and Settings reports the conflict. Pending edits are bound to the account and never uploaded to a different account. This requires the companion model-api settings endpoint and migration; until deployed, local controls work and sync reports a pending retry.

### Firm policy

The platform's Policies > Tool Permissions section can set `sandbox: { mode, value: { enabled, networkMode } }` through the existing organization-policy sync channel. An enforced policy overrides application, chat and parent choices, including preferences saved before the policy arrived. The server refuses application, chat, legacy network and policy-release attempts while it is locked. The chat hides its sandbox icon; Settings shows the firm's value and name with disabled controls. Policy changes cancel commands using the old permissions.

A firm default supplies the application value while allowing independent chat overrides. Changing the application value takes that default back through the existing policy flow. As with other firm settings, an enforced value remains after sign-out until the member explicitly confirms taking it back. Firm values never overwrite the member's personal synced preference. Both the updated platform and desktop are required; older desktops ignore policy keys they do not recognize.

## Boundary and permissions

No protected runtime has a host disk, direct host filesystem passthrough, clipboard, or host control socket. Restricted runtimes have no network device. The explicitly unrestricted runtime has an outbound-only QEMU user-network device. A guest FUSE adapter requests directory entries and file chunks from the host over a bounded virtio-serial protocol. The host authorizes every operation against the command's fixed folder grants, and keeps separate brokers and approvals for concurrent commands. The guest kernel and supervisor enforce separation between those commands; a guest-kernel compromise could reach the combined grants of active commands, but cannot make the host broker expose an ungranted host path. The command runs without root privileges and with a clean environment.

LegalWork checks shell and read permissions before starting. Folders are read-only unless the command requests writes and edit permissions allow them. `ask` requires the host's approval even when unrelated server operations use automatic approvals. Firm policies are checked directly by the command service, including when an engine still holds older settings. Agent and session restrictions also apply. Scoped shell, read, and edit restrictions apply conservatively to the entire command because Python can launch arbitrary descendants. Changing workspace, global, or firm engine permissions cancels active commands. Changing sandbox defaults cancels only commands inheriting them, and changing a chat override cancels that chat and inheriting descendants. Firm shell permissions apply to the protected tool and cannot restore the engine's host shell.

### Network modes

When sandboxing is on, the application default and each chat override offer three network modes for commands, page reads and web searches. The initial protected mode is **Approve network traffic**. All network controls are inactive while sandboxing is off.

- **Allow all network traffic** lets commands make outbound connections without a network prompt, including TCP, UDP, DNS, HTTPS, and connections to the local machine and LAN. No inbound ports are published. Existing stricter tool, agent, and session permissions still apply. If a webfetch policy is scoped or requires approval, that command uses the restricted HTTP(S) broker instead of receiving unrestricted sockets.
- **Block all network traffic** denies outbound traffic without prompting. The guest has no NIC and the host refuses network broker requests. Clearing proxy variables or using a different Python networking library does not restore access.
- **Approve network traffic** permits individual HTTP(S) requests only after host approval. Arbitrary TCP/UDP and local/private destinations remain blocked. This mode is not a generic approval mechanism for SSH, database protocols, or LAN services.

Managed engines disable the built-in `webfetch` and `websearch` routes and provide `legalwork_webfetch` and `legalwork_websearch`. These tools use the same host policy and approval service as commands, without starting a VM. The server resolves chat ancestry and agent permissions. Approval occurs before DNS or transmission; every page redirect is checked and approved separately. Search uses the desktop's Exa provider, shows the exact query and request body, and refuses provider redirects. Changing applicable settings or permissions cancels pending web approvals and active requests. Sandbox-off retains ordinary tool permissions, and allow/off permit private-network page reads. Model transport, connected apps and browser/computer tools still retain their separate permissions.

The approval enters the requesting chat's existing permission queue and inline approval panel. It uses the same waiting indicator and response flow as other chat permissions. The panel shows the agent's command description separately from the observed HTTP action, destination, URL parameters and outgoing data. Search approval shows the actual query and provider in plain language. JSON and form payloads are shown as labeled fields; protocol JSON stays in collapsed Details. Unknown fields are retained in the generic review, and a shortened preview explicitly points to the full request. Binary content is identified as unreadable. Credentials and unencrypted connections are called out. Full URL, method, headers and body remain available under Details. The agent's description is context, not a verified assessment of its purpose or risk.

Approvals apply once. Different chats can wait independently; another chat's panel cannot answer the request. Replies require host authorization and the matching request, workspace and session IDs. Agent/client tokens cannot approve. Switching chats or reloading preserves pending requests until a decision, command cancellation or timeout; a missing renderer never grants permission. Cancellation, timeout and server shutdown deny outstanding requests.

For approved HTTP and HTTPS, a guest-local proxy buffers the complete request. HTTPS is terminated with an ephemeral guest certificate; CONNECT never becomes a raw tunnel. The host binds authorization to the URL, method, final headers, and full body before DNS resolution. It rejects private, reserved, loopback, and metadata destinations and connects to the validated IP. Redirects require another request. Direct sockets and DNS have no route out, even if a script clears its proxy settings. Unrestricted commands use normal system certificate verification without this proxy.

Requests requiring approval must fit in a 16,000-character review, including the URL, headers, body and digest. Binary bodies use base64, which also counts toward that limit. Larger requests are refused without sending; the broker's 4 MiB request-body limit does not make large uploads approvable. The review limit is a remaining restriction for document uploads.

Changing the mode persists it and cancels running commands, including pending approvals and active connections. The save response waits for their cleanup. An unresponsive cleanup shuts down its VM after ten seconds. Community calculation scripts remain offline regardless of the agent network setting.

Writes are staged in private temporary files on the host, with no changes to originals during execution. After the command finishes, the guest supervisor kills any remaining command processes, verifies that its cgroup is empty, and closes its broker channel before the host applies staged changes. Publication is serialized within the server so concurrent commands cannot silently overwrite an intervening edit. The filesystem broker rejects unauthorized paths, symlinks, Windows device aliases, alternate data streams, protected execution settings, and concurrent host edits. Atomic replacement of individual files preserves external hard-link targets. Cancellation or a runtime failure discards staged changes. Applying changes is not a transaction across all files: an I/O failure partway through may leave earlier validated changes applied.

Files that will be changed or deleted receive content fingerprints, checked again before publication. This detects same-size edits even when the host reports unchanged timestamps. Files that are only read do not require a full content scan.

The engine's built-in host shell is disabled independently of the sandbox plugin. Session overrides cannot restore it. Direct terminal/shell endpoints, engine config mutation, and command-template host interpolation are blocked. Managed engine configuration discovery excludes project and home plugin directories. Explicitly installed plugins and connected MCPs remain trusted host integrations.

Installed skill instructions remain discoverable. A command may request installed skill names through `skills`; their resource folders appear at `/skills/0`, `/skills/1`, and so on. Skill and read permissions apply, and these folders are always read-only. Python document libraries (python-docx, openpyxl, python-pptx, pypdf, ReportLab and Pillow) are bundled for offline use.

## Multiple folders

Every command receives the current workspace at `/workspace` and the workspace's explicitly authorized external folders at `/authorized/0`, `/authorized/1`, and so on. Each guest path maps to its authorized host folder. Identical filenames in different folders remain distinct. Files and directory entries are fetched on demand, so a large document collection does not have to be copied before a command starts. An opened file is checked for concurrent host changes; conflicting edits are refused before staged changes are applied.

The agent can combine data from every folder it can read in that command. Read-only protects original files against changes; it does not prevent copying their contents to a writable folder, command output, or an approved network request. Use separate workspaces and avoid shared grants for matters that must remain separate. Network access is governed separately and is never granted by adding a folder.

The current Authorized Folders setting grants access at workspace scope. Shell commands mount every grant, and `write: true` makes every document folder writable after edit permission checks. Installed skill mounts remain read-only. The VM supports mixed read-only and writable document mounts, but the current settings do not offer per-folder access levels or per-command folder selection. Do not present a writable command as restricted to an output folder.

Scoped external-folder denials block exposing the whole folder; scoped `ask` rules require explicit approval before it becomes available. Removing a folder or changing permission settings cancels active commands. Removing a child grant does not revoke access through an authorized parent: remove or narrow the parent grant as well. Overlapping paths share the same staged file, and a read-only grant cannot be bypassed through a writable alias. External-folder indices can change when the grant list changes.

## Scope and limits

This isolates script execution. Model-provider requests, connected apps, browser/computer-use tools, ordinary file tools, and the LegalWork server remain host capabilities governed by their own permissions. Authorized cloud-synced folders or network drives can also cause the host OS to transfer data through their storage providers; that traffic is outside the script's HTTP broker. The sandbox does not turn an unrestricted connector into a confined tool. The host application, OS, QEMU, and signed runtime resources remain part of the trusted boundary.

Each command starts fresh. Installed packages and changes outside approved folders disappear afterwards. Commands use Linux paths (`/workspace`, `/authorized/0`, etc.), not Windows or macOS paths. There is no aggregate authorized-folder size limit or 128 MiB file limit. File transfers use bounded 128 KiB chunks; temporary edits use disk space, with a per-command budget of half the initially available space after reserving 1 GiB. Available space is checked again as edits grow. Commands can hold 256 file handles, access metadata for 100,000 files, and stage 10,000 changed paths or temporary files. These execution limits do not restrict the total collection size. Symlinks and special files are refused. `.git`, `.opencode`, environment files, shell startup files, app metadata, and private staging files are excluded; `.legalwork/scratch` is available for task files. Directory renames return EXDEV for tools to perform a copy-and-delete move; host timestamps are not preserved. HTTP request and response bodies are limited to 4 MiB and 16 MiB. There is no fixed session or concurrent-command count limit. Commands in the same server process share a VM with other commands of the same network capability. Restricted commands and unrestricted commands use separate runtimes so a restricted command never shares a guest kernel with a NIC. A server can therefore have two runtimes when both capabilities are in use (including offline calculations). Separate server processes have separate runtimes.

macOS uses Hypervisor.framework acceleration when `kern.hv_support` reports availability, with software emulation for hosts that cannot virtualize. Virtual Intel Macs also use software emulation: nested HVF exposed a guest kernel panic and hangs in CI despite reporting hardware support. Physical Intel Macs and supported Apple Silicon Macs retain hardware acceleration. Accelerator selection also checks the physical CPU, so an Intel build running through Rosetta uses software emulation for its x86 guest. Windows first tries the bundled QEMU Windows Hypervisor Platform (WHPX) backend. A successful guest boot is required before sending any command. Failed hardware startup is fully closed before software fallback, and command failures are never replayed. Accelerated boot has a 30-second deadline; software boot has a 180-second deadline. Packaging rejects Windows QEMU builds without WHPX. Machines without virtualization still run protected commands through software emulation. The app does not enable OS features, elevate or reboot automatically. If acceleration is unavailable, an administrator can enable Windows Hypervisor Platform and restart; ARM64 requires a supported Windows 11 release. See [QEMU prerequisites](https://www.qemu.org/docs/master/system/whpx.html). Docker and WSL are not required.

Windows uses a unique named pipe for the host side of virtio-serial because QEMU's Windows stdio backend can drop bytes under backpressure. Protocol 5 frames have bounded lengths and carry 128 KiB file chunks as binary through both the worker/supervisor and guest/host channels, avoiding base64 and repeated JSON parsing of file contents. Metadata and complete network approval requests remain JSON. Truncated, oversized and ambiguous frames fail closed. The guest loops on partial reads and writes. The test suite includes a multi-megabyte binary round trip and random reads from a 2 GiB input without transferring its entire contents.

Each shared VM starts on demand and stays warm for five minutes after the last command. Every ten seconds while idle it checks host memory pressure and can exit early to return all its memory. A new command cancels idle shutdown, and an asynchronous pressure sample rechecks active use before stopping a VM. Even a boot whose callers cancelled expires. Each runtime receives half the available host CPUs, capped at eight, with a minimum of two on machines that have at least two. Worker cgroups share CPU fairly. Its guest-memory ceiling is one quarter of host physical RAM, with a 2 GiB minimum and 8 GiB maximum, rather than a reservation multiplied by the number of sessions. If both network capabilities are active, each of the two VMs has this ceiling. Resident memory grows as pages are used; Windows also accounts for the configured guest memory as committed memory. A virtio balloon device with free-page reporting returns freed guest pages where the host accelerator supports discarding them, without shrinking the guest ceiling or preallocating per-chat RAM. File caches and the guest image can remain resident until idle shutdown. Idle chats do not start workers. Guest cgroups bound the combined command memory to 85% of memory available after boot and keep the supervisor outside that budget. Each command has a 512-process/thread budget, with 4,096 across the runtime. Exhausting memory can terminate a command and discard its staged writes; it does not disable isolation.

Each command gets a distinct Linux user/group identity and private mount, PID, network, IPC and UTS namespaces. Identities are never reused during a VM lifetime, including for kernel resources such as user keyrings. The shared system files are read-only; `/tmp`, `/run`, `/mnt`, `/dev` and `/sys` are private. The only exposed device nodes are null, zero, random, urandom and the root-only FUSE device. Commands run without capabilities or privilege elevation. Folder grants, FUSE requests, network approvals, output and cancellation are routed through separate worker pipes. A command cannot supply the routing identity of another worker. Temporary files use the shared memory budget and do not store authorized folders or their staged edits. Use an authorized writable workspace path for large intermediate files.

Sharing a VM also shares a kernel and failure domain. A VM crash stops all of its active commands, and a compromised guest kernel could break isolation between commands. A failed or unresponsive cleanup shuts down the VM and discards pending edits. Restricted runtimes still have no raw network interface. Neither runtime has direct host filesystem access. A compromised unrestricted guest kernel retains the unrestricted networking explicitly allowed for its commands. This is not a separate hypervisor boundary between sessions.

## Why this approach

[OpenAI's Windows sandbox explanation](https://openai.com/index/building-codex-windows-sandbox/) describes a native design using restricted execution identities and Windows access controls. [Codex Windows documentation](https://learn.chatgpt.com/docs/windows/windows-sandbox) distinguishes the elevated implementation from a weaker unelevated fallback. On macOS, [Codex's source](https://github.com/openai/codex/blob/2dae757b8713d3317e8da58828bdac821386982c/codex-rs/sandboxing/src/seatbelt.rs) uses Apple's Seatbelt through `/usr/bin/sandbox-exec`, with filesystem and network policies. Neither design requires users to install Docker. A proxy without OS enforcement cannot contain arbitrary Python.

[Anthropic's containment explanation](https://www.anthropic.com/engineering/how-we-contain-claude) describes Cowork's VM boundary using Apple Virtualization.framework on macOS and Windows Host Compute System, with trusted host integrations outside it. LegalWork follows the separation between host permissions and guest execution, using a bundled QEMU runtime with brokered folder access and a physically absent NIC for restricted commands.

We also tested Anthropic sandbox-runtime 0.0.78 on Windows 11 ARM64. Raw connections and unauthorized file writes failed, while `getaddrinfo("example.com")` succeeded. Its documented Windows DNS limitation does not meet this feature's strict network requirement. The restricted VM removes that path instead of relying on proxy environment variables or command-text inspection.

## Unsloth and MXC review (2026-10-10)

We adopted Unsloth's compact menu with descriptive options and a nested network menu, plus flat settings rows, an Off/On control, and a computer-status chip. The existing LegalWork permission approvals remain in the chat. There is no software-only security level or automatic risk approver.

We did not replace the execution backend with Unsloth's current integration. At [Unsloth commit 09ce386](https://github.com/unslothai/unsloth/tree/09ce38697ff6a928929b0ac707442b931f7dd098/studio/backend/core/inference), its [Mac profile](https://github.com/unslothai/unsloth/blob/09ce38697ff6a928929b0ac707442b931f7dd098/studio/backend/core/inference/sandbox_macos.py) permits IP networking. Its [Windows adapter](https://github.com/unslothai/unsloth/blob/09ce38697ff6a928929b0ac707442b931f7dd098/studio/backend/core/inference/sandbox_windows_mxc.py) pins an older MXC runtime, records network posture as unverified, and can fall back to software safeguards in automatic mode. That is not a replacement for our block-all or exact-request approval contract. Its software checks are not an OS boundary for arbitrary Python.

Current Microsoft MXC has advanced beyond the preview shown in the screenshots. Its [Windows networking documentation](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/networking.md) describes OS-enforced, proxy-only egress, but backend support varies with the Windows build and proxy packaging. Its [Mac backend](https://github.com/microsoft/mxc/blob/main/docs/backends/seatbelt/seatbelt-backend.md) supports kernel-enforced network denial and a loopback proxy exception, with shared host-kernel and filesystem semantics. Native execution is a promising route to lower startup and memory overhead, but changing to it requires preserving our folder grants, revocation, descendant cleanup and per-request approval broker, plus platform escape tests. The Unsloth timings use different workloads and are not a LegalWork benchmark. The verified VM backend stays in place for this change.

## Build and verify

Docker is used only to construct the guest on developer/CI machines. Release and CI workflows produce runtime artifacts for each platform and architecture, run real isolation tests, and include those artifacts in the installer. Build-time package managers are not shipped as prerequisites.

On a Mac development machine:

```sh
node scripts/sandbox/build-guest.mjs arm64
node scripts/sandbox/package-runtime.mjs "$(command -v qemu-system-aarch64)"
LEGALWORK_SANDBOX_INTEGRATION=1 bun test --timeout 180000 apps/server/src/agent-sandbox
pnpm --filter legalwork-server build
LEGALWORK_SANDBOX_INTEGRATION=1 LEGALWORK_TEST_OPENCODE_BIN=/path/to/opencode bun test apps/server/src/agent-sandbox/engine.integration.test.ts
```

For Intel, build `x64` and package `qemu-system-x86_64`. Windows packaging takes the matching QEMU executable from MSYS2 and recursively bundles its imported libraries. The Linux guest may be built on Linux and transferred as a CI artifact. `verify-runtime.mjs` checks resource completeness and hashes before desktop builds. macOS signing preserves the QEMU hypervisor entitlement and updates the resource manifest before sealing the outer application.

The VM and network integration suites start ten commands at once and verifies a shared boot ID, separate namespace IDs, isolated temporary files and loopback ports, distinct folder permissions and request approvals. They also check cancellation while another command is active, conflicts between simultaneous edits, direct TCP/UDP/DNS/HTTPS in unrestricted mode, IPv6 connections, worker-to-worker firewall denial, and separate VM boot IDs for restricted and unrestricted capabilities.

`scripts/sandbox/probe.ts` also runs with the desktop's actual Node runtime after bundling with `bun build --target=node`. It verifies direct IPv4, IPv6, UDP and DNS denial, supervisor and host-channel isolation, read-only folders, Python/Node, approved copy-back, HTTPS request inspection, approved Python and Node HTTPS with certificate verification enabled, and ten simultaneous direct TCP/UDP commands under the actual desktop Node runtime. The engine integration test uses a local fake model, makes the shipped engine call `legalwork_shell`, checks the tool identity, and attempts a direct host-shell escape. It sends no data to a real model provider.

### Network-mode validation (2026-10-09)

Before the latest firm-policy and chat-flow integration, commit `814f87b5d` passed [all 15 PR checks](https://github.com/eigenweltlabs/legalwork/actions/runs/37918757192), including real VM isolation on Mac, Windows and Linux (x64 and ARM64), application suites and Linux/Windows packaging and launch. The current PR description records subsequent validation separately.

The real Mac Electron app completed ten commands in each mode: block 3.19 seconds and allow 4.39 seconds with cold startup, and approve 1.45 seconds on a warm VM with test-harness replies. Health checks had 2.98 ms p95 and 15.49 ms maximum latency. Windows 11 ARM64 as a standard user without virtualization passed 37 tests and 205 assertions; ten unrestricted commands took 31.68 seconds. These are specific test workloads, not general performance guarantees.

A memory barrier held ten workers with 32 MiB allocated each. Both systems used one QEMU process, one shared boot ID and ten distinct users. Resident memory was approximately 1.7 GiB for the shared runtime. Windows committed memory reflects the configured shared guest ceiling.

The chat integration was exercised in Mac Electron with a synthetic example.com request. The request appeared in its originating chat, stayed out of another chat, survived switching and reload, and completed through the inline Allow once button. An unanswered request timed out and disappeared. Tests cover ten independent chat approvals, host-only replies, wrong-chat/workspace rejection, stale replies, engine snapshot reconciliation, and the inline panel's one-time controls. No real model provider was contacted during these tests.


### Performance reproduction

Run `bun scripts/sandbox/benchmark.ts apps/server/resources/agent-sandbox/runtime --idle --memory` against the packaged assets. The script separates integrity verification, cold boot, three ten-worker CPU trials, document imports, an 8 MiB verified binary round trip, reuse after 35 seconds idle, and resident memory during/after a 384 MiB allocation. Its memory barrier is a denied synthetic HTTP request; no data is transmitted. For Windows, bundle the script with `bun build scripts/sandbox/benchmark.ts --target node --outfile benchmark.mjs`, then pass the runtime directory to the native Node executable. Runtime logs identify the actual accelerator, CPU allowance and shared memory ceiling.

Hardware acceleration must also be validated on a physical Windows machine with WHPX available. The development Windows VM lacks nested virtualization and exercises automatic software fallback. Passing that test does not establish accelerated Windows performance.
