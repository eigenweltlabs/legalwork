# Native Back Office

The implementation starts from LegalWork dev f646f475. Its platform counterpart is `codex/back-office-native` in model-api, based on main b704f9c. Deploy the platform migration and API before enabling a firm's Back Office policy. The combined branches have local integration coverage against disposable Postgres and two temporary desktop SQLite stores.

## UI and licensing

The native renderer consumes MIT-licensed `twenty-ui` 2.54.0 at an exact version. Installation respects the repository's release-age policy. Its actual buttons, input controls, select menus, popovers, calendar picker, chips, avatars, tabs, lists and dialogs are used. Root CSS declares the Twenty layer after Tailwind's base layer. A scoped ThemeProvider keeps Twenty's typography and portal styling inside the module.

The published MIT library does not contain Twenty's application record table. That application source is AGPL and is excluded following the user's MIT-only decision. The local grid and application workflows use the installed components and the live Twenty preview as their visual reference. Create uses a record panel, simple text fields edit in place, and field creation uses settings pages. The view selector uses Twenty’s compact create/edit flow for Table, Kanban, Calendar and List. Cards, list rows, menus, pickers and dialogs reuse MIT library primitives. Saved view IDs stay in the URL so switching does not reload the page and reopening restores the layout. The MIT notice ships in desktop resources/licenses as well as the source notices.

## Data and APIs

The versioned shared definition is `packages/types/src/back-office.ts`. Its platform copy must stay aligned. SQLite stores model definitions, stable record IDs, per-record revisions, views, an audit trail and a team outbox in the existing runtime database. Required core IDs, types, cardinality and visibility are protected. Custom objects and fields can extend the model. Archive and restore preserve identity.

Default model version 3 removes provider-specific IDs from the first preview templates. Existing import identities move to record metadata, outside the editable data model. CSV imports use an optional source-ID column and generic `source:` relationship references. Upgrades preserve firm labels and extensions. Destructive conversions remain blocked. Shared definitions are updated online and arrive before dependent records. A model preview validates existing values and reports affected record counts before applying populated-object changes.

Project connections use the existing project metadata system. A `backoffice` field names any visible object, including custom objects, its single/multiple cardinality, and a nullable value containing the directory identity and stable record IDs. The project Home picker reuses the table's CellEditor; selected names open the picker and the adjacent arrows navigate to the record panel. Project filters key references by object, directory and record identity and resolve current names. The Legal Matter template contains only the many-to-many matter reference. Matter-owned details and client/organisation relations stay in Back Office. Internal, contract and research templates retain their project-specific fields and references. Untouched older starter templates are upgraded; customized definitions and populated text values are preserved. Project metadata remains in project.json and uses the existing metadata sync and conflict handling. The platform accepts the same extended union in JSONB without a SQL migration. Older platform versions need this schema update before syncing reference fields.

Local directory identity uses the persistent device identity; shared identity hashes the normalized platform URL and organization, independent of team member. References from another directory remain unresolved, never bound by name. No protected record names or content are copied into metadata. The legacy `projectLinks` storage is retained internally for compatibility, but the separate project/matter linking panels and creation endpoint are removed.

The renderer and native agent tools consume the same validated Back Office routes. The current-project context tool resolves all metadata record fields through current directory permissions. Record, model, view and relationship changes use revision checks and current permissions. Agent-originated writes are attributed in the audit trail.

## Team sync

`backOffice.sync` is an enforced opt-in organization policy. Model administration, directory editing and billing access are independent. Project permissions remain independent of matter access. The UI and agent automatically select the firm directory when the enforced setting is active, otherwise local storage. The UI has no storage selector or everyday publishing action. The existing publishing API is retained for a one-time migration of existing local records, with a reviewed preview preserving IDs and warning about same-name records. Projects must already be shared before their local IDs can be translated into shared project IDs.

Publishing preserves the existing team model and adds compatible local extensions. Shared labels and fields survive publishing from a desktop with an older local model. Conflicting field types, relation targets, cardinality or visibility block publication for review.

Offline writes retain stable operation IDs. The first rejection blocks dependent operations. Comparisons show team values and proposed fields; users can reapply those fields against a checked current revision or explicitly discard the queued record chain. Unspecified fields survive updates from older clients. Authorization rejection clears the managed replica and retains proposals for resolution. Transport failure retains the offline replica. Policy pokes trigger revalidation after policy refresh.

Publishing creates identities before optional relationships, with required relationships ordered by their dependencies. Cyclic required relationships need to be made optional before publishing; the operation is rejected without partial staging. The initial full-snapshot platform transport is limited to 10,000 stored records and needs pagination before that limit is increased.

The server's build bundles `back-office/schema.ts` into its runtime dist, keeping packaged Electron independent of workspace TypeScript sources. The renderer's components are bundled by Vite. Packaging checks use Node's 8 GB heap allowance for the existing large renderer build.

## Validation

Feature tests use `bun test apps/server/src/back-office/back-office.test.ts` in LegalWork and `vitest run src/lib/back-office/permissions.test.ts` in platform. Type checks, server and renderer builds, help generation and manual native UI comparisons supplement those tests.

For cross-repository integration, run the platform's `vitest.integration.config.ts` with `TEST_DATABASE_URL` pointing to a disposable Postgres and `LEGALWORK_TEST_CHECKOUT` pointing to this checkout. Select `src/lib/__integration__/back-office.test.ts`, `src/db/__integration__/row-security.test.ts` and `src/db/__integration__/migration-upgrade.test.ts`. The native fixture runs the real sync client against the platform HTTP route handlers, including reviewed publishing, project ID translation, multi-batch synchronization, conflicts, model ordering, persistence and access revocation. Clerk identity lookups are substituted. The ordinary integration command skips the cross-repository case unless the checkout variable is supplied. No live platform deployment is involved.

Saved views include layout type, icon, Kanban grouping, calendar date field and day/week/month mode. Existing views default to Table. Native and platform writes merge omitted view properties with the existing definition so older clients preserve newer layout settings. Deletion is a synced archive flag and retains records. These JSON additions do not require another SQL migration.

Record movement uses renderer pointer events rather than OS-native HTML dragging. It cancels on pointer release/cancel, Escape, window blur, visibility loss and unmount. Keyboard users can change stage/date through the field editors. Native drag automation was stopped after an OS input issue; the replacement pointer gesture has type/build coverage but still needs a human interaction check.

## File fields

Template 4 adds Signed agreement and Invoice PDF. File values contain immutable descriptors (UUID, owning record/field, filename, size, MIME type and SHA-256), rather than paths. Custom file fields support one or up to twenty files, each capped at 10 MiB. Native payloads live below the runtime directory in `back-office-files`; reading requires current record and field access. A required-file draft can reserve a record UUID and save with explicit `create: true` after attaching its files.

The renderer reuses the document preview in read-only mode, with MIT Twenty file controls and a project-copy picker. Selecting a project file deliberately creates a copy governed by the destination record/field; it does not expose the original project. Unsupported active content is offered for download instead of inline execution. Agents can attach a copy from an accessible local project with `legalwork_back_office_attach_file`, then save its returned descriptor in a file-field array.

The platform companion requires migration 0052 for tenant-isolated attachment manifests and durable object-deletion capture. Upload links target staging objects. Commit verifies size/hash and writes the already-verified bytes to an immutable final key. Sync preserves operation order and sends model changes before preparing files in dependent fields. Record references are accepted only after verification. Downloads require current record/field access and use expiring storage links. Removal of a field reference revokes its download route while audit/version data remain intact. Local file operations do not call this platform API unless sharing is enabled.

Default model version 5 broadens Companies to Organisations, with an optional organisation type for companies, courts, public authorities, law firms, associations/nonprofits and other institutions. Stable object and field IDs are retained so existing relations, project metadata IDs and signed history remain connected. Untouched labels are updated, firm customizations are preserved, and legacy organisation labels are upgraded transactionally. Contract counterparty fields select organisation records; courts and opposing parties for matters belong to Back Office records.

Default model v7 removes the redundant protected Clients.clientType field. The person/organisation relation identifies the linked entity. Upgrades remove the old current values and saved-view references transactionally; existing relations, custom fields and signed historical values remain intact. A firm-created unprotected field using the same ID is preserved.

Default model v6 adds editable People.personType select options and an Active boolean. Starter team types are initial options, not a schema enum. New People values default to Active=true and External contact when that option exists. Upgrading existing people initializes Active without guessing their type.

Back Office project-reference fields carry optional `filters: {mode: "all" | "any", conditions: [{fieldId, operator, values}]}`. The shared evaluator supports normal-visible scalar/select/relation fields and rejects unavailable or restricted filter fields. No record names are copied into definitions. The native authoring routes validate new record IDs inside the existing project write queue. Empty initial field definitions do not open Back Office, so creating a project stays independent of directory availability. Existing IDs are grandfathered when type/status or filter definitions change; sync transfers already-authored assignments without reapplying current eligibility. `legalwork_project_reference_options` searches eligible records with current permissions and returns selected records separately. Filters and new defaults are carried by the shared wire schemas; no SQL migration is required.

Agent CRM workflows use the bundled project plugin in both the Assistant and regular chats. `legalwork_back_office_discover`, `records`, `save`, `model_preview` and `model` expose the actual editable schema and record CRUD. Fixed guidance identifies Back Office as the CRM store, instructs reuse before creation, follows discovered relation dependencies, distinguishes record relation IDs from project `{directoryId,recordIds}` values, and requires link verification. Live project configuration remains a conversation reminder, preserving system prompt caching.

The Assistant's scoped metadata setter accepts the shared project value schema, including Back Office references. `legalwork_assistant_project_reference_options` and `legalwork_assistant_project_back_office_context` reuse native project handlers after Assistant project-access checks. Regular-chat details/options/metadata/context/setup tools accept an explicit `projectId` so creating a new project does not redirect subsequent writes to the originating chat. Agent setup and delegated intake use the same CRM instructions. A CRM write and a project write are separate commits: partial progress must be inspected and resumed, not described as an atomic transaction or blindly retried.

Assistant project search resolves current, permission-filtered linked record values instead of stringifying reference objects. It loads a directory snapshot lazily once per search and never persists copied names. `backOfficeUnavailable` marks an incomplete linked-record search; it is not evidence that a client or matter is absent.

Relation value pickers share inline record creation through `RecordCreationProvider` and `RecordCreateForm`. The same editor is used by tables, record panels, saved layouts, project metadata and relation-valued metadata filters. Project-list record filters expose the same creation form. It reads the current model, supports required/custom fields and nested relations, reserves a UUID for retry safety and required attachments, and saves through the normal signed record route. The optional `directoryId` write guard rejects a stale directory before any record is written. Current permissions/model and filter eligibility are rechecked before creation. Unique equality filters can initialize values; multi-option internal types require a choice rather than guessing a person's role. Created records are cached immediately, placed first in the picker and selected without replacing an existing multi-selection. Closing an in-flight form never assigns its later result, and cancelling a parent does not delete explicitly created child records.

The template upgrader recognizes exact previous English/German starter definitions, including older text/reference variants, and replaces an untouched Legal Matter preset with the matter link only. Empty/custom templates and saved projects are not rewritten. Agent linked-record context follows the current permission-filtered forward relations, with cycle deduplication, so matter-only projects remain searchable by their clients and organisations without denormalized project values.
