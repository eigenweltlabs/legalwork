# Local mail scheduling

Scheduled send extends the existing Outbox. Gmail, Microsoft Graph and SMTP keep their current credential custody, immutable MIME, sender validation and uncertain-outcome recovery. There is no provider-side scheduler, parallel submission journal, always-on server or new OAuth grant.

Schema 35 adds encrypted `mail_outbox_schedules`, keyed by account and action with a cascading Outbox foreign key. Queueing commits the MIME snapshot, action, fixed UTC instant, display zone and journal `available_at` in one transaction. The existing submission claim cannot acquire it before that time. A repeated submission of the same draft version returns the same action only when its schedule agrees. An immediate-send entry point cannot promote a previously scheduled snapshot.

Rescheduling requires the current action generation/revision, a still-queued non-cancelled action, an existing schedule and current account/sender credentials. It cannot update a claimed, dispatching, uncertain, failed or restored submission. The atomic update changes the due time and revision without rebuilding MIME, changing recipients or assigning a new Message-ID. Cancelling and editing use the existing Outbox controls. The edited draft requires a fresh send decision.

The runner rechecks due time before connection preparation and immediately before its dispatch boundary, including after a system clock rollback. Temporary preflight outages retain a safe retry and do not exhaust a scheduled message's attempt budget while offline. Existing backoff still applies. Permanent failures require attention. Once dispatch is marked, transport loss remains uncertain and cannot become a safe retry or reschedule. Startup recovery, cancellation and reconciliation use the existing journal semantics.

Execution is local and depends on the device clock and provider reachability. Closing or locking the encrypted mail service stops its worker. Desktop sleep and persistent mail pause suspend the runtime. On macOS and Windows, screen-lock events also suspend it; startup checks the current lock state before unlocking Email. These use [Electron powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor/), whose initial locked state is available on supported systems. Resume/unlock applies the latest state without overriding a user pause. No wake assertion is held for a future send. Overdue work is eligible when execution resumes; this is an earliest-attempt guarantee, not a delivery deadline. Standalone services must supply their own lifecycle control.

The picker round-trips wall times in the selected IANA time zone and exposes distinct offset candidates for repeated times. Missing clock times are rejected. Confirmation stores the selected instant, so later system-zone changes do not reinterpret it. New schedules are bounded to 366 days. The UI uses shared fields, selectors, buttons, alerts and dialogs; full setup and execution details live in the user manual.

Headless tests cover encrypted migration rollback/reopen, private worker persistence while offline, immutable snapshots, duplicate queue entry points, due-time dispatch, clock rollback, optimistic rescheduling, account scope, cancellation, offline catch-up and uncertain restart. Pure picker tests cover hour and half-hour transitions, missing days and fractional offsets. Desktop lifecycle tests inject fake power events and notifications without importing Electron or changing Mac focus. The shared time picker has standard-profile Mac acceptance through Snooze, including a saved future time and daylight-saving validation. Successful scheduled provider dispatch remains unverified.
