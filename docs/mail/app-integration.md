# Mail integration — EIG-174

Ticket: https://linear.app/eigenweltlabs/issue/EIG-174

Mail remains a component of the shared Legalwork shell. This pass adds the missing attachment → explicitly chosen workspace → existing/new chat draft → source email journey. It reuses workspace endpoint resolution, workspace file writes, chat composer state, internal file targets, the shared dialog/button components, and the existing Mail reader. No schema migration is required.

## Copy and return semantics

Chat copies use a new `.legalwork/attachments/<random-id>/` directory, so repeated original filenames do not replace previous copies. Names are bounded and Windows reserved filenames are handled; the original label remains in the mention. The matching `.mail-source.json` records the account label, subject, locator, verified reference and SHA-256, copy path and return link. These are ordinary workspace files after explicit copying, subject to that workspace's access, retention and backup rules; they are not part of encrypted local Mail custody.

Both extraction and the final File passed to the copy helper are hashed. Source and target checks run before copying and again before staging the draft. Cancellation during an in-flight workspace write may leave the requested copy; it never stages a chat draft or submits a model request. Retrying can create another separate copy. A completed copy/provenance record is not automatically removed if Mail becomes unavailable afterwards.

The source record retains the historical local server origin as provenance only. The durable link does not use it for routing, so a local server restart on another port works. Live native notification targets still require their original server origin to match. A source link cannot choose a remote server, carry a host token, expand account access, or bypass the current profile's authorization. A different/restored profile must contain the same accessible source/reference/hash; otherwise the return is unavailable. The composer source affordance is in-memory; the ordinary Markdown link and copied source record persist with the user's saved/sent chat content and files.

The chat picker currently lists up to 100 root chats in the selected workspace. All registered workspaces are available; existing selections are checked against their workspace directory before copying. Ordinary unrelated shell renders preserve the selection and prepared destination. Copy-to-chat is bounded to 32 MiB per attachment; endpoint permissions, request deadlines and remote availability still apply. No model call happens until the user separately sends their chat draft, at which point the workspace's configured model/tools may receive the copied material.

## Native save publication and filesystem limits

Native Save is bounded to 64 MiB and 120 seconds, with at most two pending exports. Suggested names preserve extensions within 160 UTF-8 bytes. Existing targets remain untouched while download/verification runs. Publication stages a private file in the selected directory, checks that the selected target did not change, and renames for a native-dialog-authorized replacement. A new destination is published with an exclusive hard link so an intervening file cannot be overwritten.

If a filesystem or mounted service rejects hard links, publication falls back to exclusive `wx` creation and a bounded copy of the already-verified staging file. It checks cancellation between chunks, fsyncs the result, and cleans its own partial file on error/cancellation; a replaced or racing destination is never removed or overwritten. **Fallback publication is not atomic**: another observer may see a partial new file until copying finishes. Unsupported-link, collision, cancellation, disk-error and replacement-cleanup behavior is covered with synthetic filesystem adapters and real temporary files. Actual FAT/exFAT/mounted filesystem qualification remains a platform gate. The browser download fallback has browser-managed collision behavior. The common connected-storage Save API is the appropriate explicit flow for remote storage. Actual Windows/filesystem coverage remains a final platform gate; no user's filesystem or profile was used here.
