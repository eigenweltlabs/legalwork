## Custody model and storage inventory

A random 32-byte database key is wrapped in Electron main using the pinned Electron 35.7.5 `safeStorage` API. Only its wrapped ciphertext is published in `mail-key-v1.json`; the wrapping protection is supplied by the OS. Provider access/refresh tokens, IMAP passwords and SMTP custody are records inside the encrypted database, **not separate per-token OS credential-store entries**. Their at-rest protection depends on that OS-protected database key. There is no plaintext fallback or renderer key API.

Electron documents macOS Keychain protection and Windows DPAPI's OS-user boundary. DPAPI does not isolate applications running as the same OS user. Consistent macOS signing identity is needed for reliable Keychain identity across updates; this audit does not infer that property from unsigned fixture runs. See the [official safeStorage documentation](https://www.electronjs.org/docs/latest/api/safe-storage). The current implementation uses the synchronous API available in the pinned runtime; newer asynchronous APIs are not claimed as shipped.

Worker stdout is a supervised protocol pipe, not an application log; maintenance errors use fixed results and stderr is discarded. Source inspection found no `crashReporter`/Sentry upload initialization in the audited app/server/desktop sources. This does not certify OS crash dumps, vendor crash handling, swap, filesystem snapshots, GPU memory or arbitrary same-user processes. ## Lifecycle and recovery

Startup automatically unwraps an existing key after actual OS-vault preflight. Missing, corrupt or unwrappable keys never silently replace an existing store. Atomic key publication uses an exclusive temporary file and no-replace link; concurrent creators reread the winner, and returning POSIX readers fsync publication. The key buffer is copied only for private initialization and cleared where the managed APIs permit; JavaScript strings/native allocations cannot be promised physically erased.

Lock/stop revokes the service epoch, stops and reaps network/file/extraction workers, closes the database and clears held key buffers. It is an internal lifecycle/custody boundary, not an additional manual-lock requirement for normal use. Account disconnect removes usable provider credentials and locks provider-backed content while retaining encrypted copies; explicit reconnect is required. Offline archive identity remains independent of provider credentials.

Rotation creates and validates a new encrypted generation under a fresh OS-wrapped key, then atomically promotes the generation pointer. Recovery authenticates a backup, verifies all published bytes and retained manifests, migrates a fresh candidate and only then promotes it. Wrong credentials, missing chunks, damaged snapshots and cancelled workers cannot promote an incomplete candidate. Restores clear provider secrets, revoke agent grants and quarantine outbox, remote-draft, portability and connected-storage work; reconnect cannot replay old sends/uploads. Previous encrypted generations and backups remain retained: rotation is not physical erasure.
