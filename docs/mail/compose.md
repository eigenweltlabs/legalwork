# Compose, replies and MIME (EIG-142)

Mail's existing right reader pane hosts a compact composer. Compose and Drafts live in the mail toolbar; the reader has Reply, Reply all, Forward and Forward as attached message. Account and sender are explicit. Sender entry is draft data, not authorization: sending remains disabled until EIG-146 supplies outbox execution. EIG-145 and shared-mailbox integration must supply the actual authorized identity list.

Draft changes immediately enter a serial CAS save queue. Saving continues across component navigation, and saved snapshots reopen from encrypted storage after restart. Incomplete recipient entry is retained in optional `content.editor` fields while parsed recipient arrays remain typed. A conflict offers Save as new draft without overwriting the existing version. The composer shows Saving, Saved locally or an error; unfinished uploads/save failures cannot be closed with its close button. Like any asynchronous save, force-quit before acknowledgement cannot promise persistence. There is no plaintext browser storage. **Pending failure boundary:** unacknowledged or failed saves live only in the in-memory queue; leaving the route can hide the error, and restart can lose those unsaved edits. Navigation-safe recovery/retry is still required in EIG-143. Mail locking clears the composer; saved drafts remain available after unlocking.

Rich text supports bold/italic, safe links/lists/quotes and inline PNG/JPEG/GIF/WebP. Pasting inserts plain text. Stored HTML is inert, and the editor uses a small allowlist; scripts, active elements, event attributes and remote image sources are stripped. Inline `cid:` images preview using verified bytes from an immutable saved draft version. Forwarding quotes plain text or includes an uploaded `.eml`; forwarding text retains downloaded attachments and refuses to silently omit unavailable ones. Reply-all uses Reply-To, excludes the selected sender, deduplicates To/Cc and never copies Bcc. References are read from the original MIME when available; Reply source reads use the existing 64 MiB reader limit; an attached forward must fit the 10 MiB attachment limit. Text forwarding does not need original MIME.

## Contracts

`local-view.ts` adds optional editor state, `inReplyTo`, `references`, attachment `disposition`, `contentId`, optional verified `bytes`, and nullable `locator` for local uploads. Existing content snapshots parse with defaults. No database migration is needed.

`POST /mail/v1/accounts/:accountId/drafts/upload` accepts `{uploadId, offset, data, complete, totalBytes, sha256, cancel?}`. `data` is canonical base64 with at most 16 KiB decoded bytes, keeping requests within the existing HTTP/worker frame bounds. Result: `{uploadId,nextOffset,bytes,referenceId}`; referenceId is null until final SHA-256 and length verification succeeds. Account/owner/connected-state checks precede every operation. Offsets are compare-and-swap; an exact last-chunk retry is idempotent. Cancellation deletes only that account's staging object and never published or pinned content. The client cancels failed uploads. Interrupted stages can resume with the same upload ID or be explicitly cancelled; there is no automatic age-based garbage collection in this ticket.

Uploads reuse encrypted blob objects/chunks and publish `draft:sha256:<digest>` references. Repeated content uploads verify/reuse the existing digest publication and delete duplicate staging bytes; final-chunk retries remain idempotent after reopen. This prefix is not sufficient authorization: saves require an account-owned publication and reads require a pinned draft version/ordinal/reference. Existing provider attachment references retain their original locator. Draft snapshots and submission intents retain immutable references even after logical draft deletion.

Limits: 10 MiB per attachment, 20 MiB aggregate attachments, 20 parts, 24 KiB combined draft JSON (including both body representations), 50 MiB of staged account uploads, and 30 MiB encoded MIME. The UI checks known attachment sizes; the store independently checks actual reference sizes. Recipient history is derived from the up to 25 saved drafts for the account in encrypted storage, including its private Bcc entries; it is never exported.

`mime/compose.ts: buildMailMime(content, {authorizedSenders, attachment, messageId?, date?})` returns `{raw,envelope,messageId,requiresSmtpUtf8,requires8BitMime}`. The attachment callback must retrieve the exact immutable draft version's bytes and verify their hash; `composeAttachmentBytes` demonstrates bounded verified reads. EIG-146 must persist/reuse messageId/date/bytes for retries, authorize From using provider identity rules, and apply transport capability checks. The builder rejects incomplete editor addresses, unauthorized senders, header injection, invalid inline IDs/types and oversize content. To/Cc are visible headers; Bcc exists only in the envelope. SMTPUTF8 mailbox addresses and non-ASCII message identifiers are explicitly rejected before serialization; `requiresSmtpUtf8` is therefore false for supported outgoing headers. UTF-8 subjects and bodies, multipart alternative/related/mixed, RFC2231 Unicode filenames and `message/rfc822` attachments are supported. An attached original's Bcc header is removed before recipient-visible serialization. Raw attached-message bytes retain their original high bytes; the serializer never attempts to reinterpret those bytes as Unicode text. No provider is contacted by the builder.
