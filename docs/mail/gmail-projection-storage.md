# Gmail run and MIME projection storage (schema v6)

`GmailRunStore(database, ownerId)` persists one current Gmail generation per account. `startOrResume(accountId)` preserves its generation and fixed 30-day `recentAfter` boundary, increments the revision to fence prior engines, and retains retry advice and `failureCount` (0–5). Completed runs are returned unchanged; creating a new scan is not implicit. `setState(accountId,{generation,revision},state,details)` is an atomic CAS. `assertCurrent` requires the exact active run stamp. Engine code must persist pause before aborting and reset the failure count explicitly after successful discovery. The existing journal owns separate `gmail:recent` and `gmail:all` scope cursors and distinct jobs; there is no duplicate cursor storage.

`progress(accountId,generation)` counts raw jobs once across scopes, current published originals, complete current projections, and pending/failed jobs across all kinds. Both scopes must have finished discovery before `enumerationComplete` is true. Projection counts require a matching current raw/body, enumeration, published current manifests, and every recorded attachment. Counts do not rehash all bytes or assert a consistent provider snapshot. Enumeration retry metadata lives on the run because a failed page request may not have created a job yet.

`putGmailMetadata` stores internal date, thread ID and exact label IDs in an owner-checked transaction. It also updates the canonical thread/memberships while preserving MIME subject/RFC Message-ID. Missing labels get ID-named placeholders; known display names remain intact. Thus provider envelope metadata remains usable even when MIME parsing fails.

`createStoredMimeProjector({database,ownerId})` returns the engine's `projectRaw` callback. Input is `{accountId,locator,reference,work,assertCurrent,signal?,source?}`; default source is the encrypted original. The supplied `assertCurrent` is a **synchronous run/credential fence only**, since the compositor separately checks the executor lease. It must not reenter the sync journal inside completion callbacks.

Attachments are streamed into encrypted storage under the parser's stable part IDs. Each publication checks raw identity, run/credential state, and lease. Enumeration remains false during parsing. Only resolved parser validation permits publishing one encrypted JSON body envelope `{version:1,bodies:[{partId,contentType,text}]}`. Its final publication transaction stores decoded MIME subject/address/date/Message-ID metadata, body descriptors, attachment filename/content type/disposition/CID/ref metadata, and enumeration, and calls `work.complete` atomically. The engine must not separately complete this body job. The original is never rewritten; HTML remains an untrusted stored projection, not rendered content.

Parser failures retain the original, record a fixed projection error under current fences, and leave completeness false. Partial attachment bytes may already be durable and remain recoverable; they are not counted as a complete projection. Lost credentials, run revisions or leases prevent even a late error from overwriting newer state. Internal repositories and callbacks remain trusted code, not a sandbox for externally captured mutable capabilities.

Historical projection metadata is keyed by account/message/raw reference, and immutable blobs remain retained. A changed raw reference triggers deletion of current derived manifests and clears enumeration. Re-publishing the same reference leaves a valid projection intact. These triggers do not delete raw bytes, labels, jobs or old projection records. Returning to an old raw hash still requires rebuilding its current derived associations before it can count as projected.

## Evidence

`pnpm --dir apps/server exec bun test src/mail/storage/gmail-projection.test.ts` launches actual Node using encrypted Multiple Ciphers SQLite and the pinned MIME parser. Synthetic cases cover durable resume/CAS/retry state, provider envelope despite malformed MIME, decoded German headers/body/attachment bytes, encrypted DB/WAL and reopen, raw invalidation/idempotence, credential-change fences, missing-attachment progress, and atomic v5→v6 migration rollback. Legacy fixture downgrades explicitly remove v6 tables/triggers before exercising older migrations.

No live provider or browser consent is exercised by these storage tests. Schema v6 and the compositor do not implement worker/API lifecycle, a mail reader, sanitization, provider deltas, or new-generation rescan policy.
