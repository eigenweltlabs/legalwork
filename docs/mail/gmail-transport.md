# Gmail full-history read transport

> Historical implementation checkpoint. Current setup and real-provider evidence are tracked in [EIG-173 qualification](live-provider-qualification.md); later automatic sync, SMTP/outbox and personal Microsoft support supersede earlier future-work statements below.

`providers/gmail.ts` exports `GmailReadTransport`. It performs only authenticated GET requests to fixed `https://gmail.googleapis.com/gmail/v1/users/me` paths. Tokens stay in trusted worker memory and Authorization headers, never request URLs, diagnostics or returned metadata. The caller supplies a valid account-bound access token; token refresh, permission verification and credential-generation checks remain outside this transport. There is no mailbox traffic in the tests.

## Exported contract

Construct `new GmailReadTransport({accessToken, fetch?, timeoutMs?, maxRawBytes?})`. `fetch` is an internal test seam, never a user-selected URL/network capability. Defaults are a 30-second deadline per operation and a 64 MiB decoded MIME cap. Timeout accepts integer 10 ms–120 seconds; decoded cap accepts 1 byte–128 MiB. Construct a fresh transport when the caller obtains a new access token; no refresh or credential persistence happens here.

- `listLabels({signal?})` returns `{labels:[{id,name,type}]}`, preserving system/user label classification. Gmail lists all labels in one response; this transport caps it at 4 MiB, 10,000 labels and 4 KiB per UTF-8 name. It never silently truncates. [Labels API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels/list).
- `listMessages({pageToken?,pageSize?,signal?})` returns `{messages:[{id,threadId}],nextPageToken,resultSizeEstimate}`. Every request sets includeSpamTrash=true, with no search or label filter. Page size defaults to 100 and accepts 1–500. The next token is returned exactly as received, encoded as a query parameter on the next explicit call. A missing next token yields null; resultSizeEstimate is an estimate, never proof that all messages were synchronized. [Messages list API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list).
- `consumeRaw(messageId, async chunk => ..., {signal?})` fetches format=raw and returns `{id,threadId,labelIds,historyId,internalDate,sizeEstimate,rawBytes}` only after all chunk callbacks succeed. The returned message ID must equal the requested opaque ID. History ID/internal date remain decimal strings, preserving history IDs beyond JavaScript's integer precision. `sizeEstimate` remains an estimate, not a decoded-size assertion. [Messages get API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get), [message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages).

IDs are bounded printable ASCII (1–256 bytes; standalone dot segments rejected), not parsed as numbers or restricted to hexadecimal. Page tokens accept 1–4096 printable ASCII bytes. They are never interpreted as links. Duplicate IDs, malformed/null arrays, invalid continuations and an immediate repeated continuation token fail invalid_response. The caller must detect longer token cycles and duplicates across pages without silently dropping work. An empty page may still carry a continuation; follow it explicitly. Listing is not a point-in-time snapshot: later history reconciliation remains necessary.

## MIME bounds, memory and sink contract

Gmail raw data is base64url inside a JSON response, not a standalone MIME byte stream. Without a custom streaming JSON parser, this implementation buffers the bounded encoded envelope, validates all metadata/base64url, then incrementally decodes and awaits each sink write. It accepts canonical unpadded or legitimately padded base64url, rejects invalid padding/unused bits, and allocates no full decoded MIME buffer. Each sink chunk contains at most 48 KiB. No heavyweight parser dependency was added and MIME structure is not parsed here.

The encoded JSON cap is `ceil(maxRawBytes / 3) * 4 + 65536`: approximately 85.4 MiB at the default cap, 170.7 MiB at the maximum. The 64 KiB allowance covers JSON envelope/metadata. These are response-size bounds, **not peak-process-memory bounds**. Retained HTTP chunks, concatenated response buffer, decoded JSON text and the parsed base64 string can coexist; depending on string representation and GC, several times the encoded cap may be live. Budget roughly 3–6 times encoded size plus runtime overhead until measured. The initial executor must allow **one raw request at a time**, not concurrent raw downloads. Larger-scale streaming needs a separately reviewed incremental JSON/base64 implementation.

All metadata and encoding are checked before the first sink call. A sink callback is awaited before the next chunk is delivered. Timeout/cancellation rejects even when an injected fetch or sink ignores AbortSignal; checkpoints prevent later sink calls and a successful return after expiry, including when synchronous processing delayed timer delivery. The transport cannot undo already written provisional chunks or interrupt arbitrary synchronous sink code. The caller must check its own cancellation/generation fence and publish bytes only after this promise succeeds and its durable content-store finalization succeeds. A consumer exception becomes consumer_failed without reflecting storage text.

`raw_too_large` and `response_too_large` are explicit incomplete outcomes. The executor must retain the message ID as pending/attention with a retry-visible reason, abort/discard provisional content and refrain from declaring account/message completeness. It may durably checkpoint listing only after every listed ID is represented by a durable job; an oversized item is not permission to silently drop it. The limits are client resource policy, not a claim about Gmail's maximum accepted message size.

## Provider failures and retry policy

Errors expose only a fixed `GmailTransportError.code`, retryable and nullable retryAfterMs. HTTP 401 becomes access_token_rejected: the caller should evaluate refresh before asking for new consent. Allowlisted insufficientPermissions becomes reconsent_required; domain policy/other forbidden responses remain forbidden. User/project rate-limit reasons and HTTP 429 become rate_limited; daily/project quota exhaustion becomes quota_exceeded. HTTP 408/5xx and network failures become transient; HTTP 404 is not_found and must not be treated as durable deletion without reconciliation. Other status failures become request_rejected. [Google error guidance](https://developers.google.com/workspace/gmail/api/guides/handle-errors).

Only rate_limited, transient and timeout have retryable=true. Quota exhaustion is visible for operator/quota-reset policy, not a hot retry loop. Retry-After accepts bounded numeric seconds or an HTTP date and returns nonnegative safe-integer milliseconds; malformed values become null. The scheduler must honor valid long delays without overflowing platform timers. No automatic retry or sleep occurs here. Raw Google error messages, response bodies, IDs and transport/consumer exceptions are never reflected or logged. Error JSON reads are capped at 64 KiB; success label/page/raw envelopes have their separate caps. Redirect following is disabled for every request.

## Validation and integration limits

```sh
pnpm --dir apps/server exec bun test src/mail/providers/gmail.test.ts
pnpm --dir apps/server exec tsc -p tsconfig.json --noEmit
```

Synthetic tests cover pagination including spam/trash, opaque IDs/tokens, raw-byte round trips, awaited chunk sequencing, strict base64url padding/unused bits, decoded/envelope limits before writes, malformed metadata, provider failures, deadlines, ignored-abort fetch/sinks and secret-free errors. Three additional smoke tests compile the module and run in actual Node with injected HTTP. Official docs were checked on 9 September 2026.

This is transport preparation for [EIG-128](https://linear.app/eigenweltlabs/issue/EIG-128/implement-full-history-gmail-and-workspace-synchronization), not a completed full-sync executor. Durable listing/job checkpoints, encrypted content sinks, MIME/body/attachment extraction, history reconciliation, refresh scheduling and live test-account qualification remain separate integration work. No real consent or mailbox read was performed.

History polling uses `users.getProfile` before the first enumeration request, then replays `users.history.list` from that durable anchor. History IDs remain decimal strings and are compared with `BigInt`; only a terminal page advances the anchor, in the same database transaction as its changes and download jobs. Specific history event arrays are used instead of the duplicated cumulative `messages` array. History pages are limited to 4 MiB, 500 records, 1,000 changes and 10,000 label entries. The default polling interval is 60 seconds while the worker is unlocked and sync is running; pause/reopen requires explicit resume. No push subscription is created.

An expired history cursor (HTTP 404), or legacy enumeration without a prior anchor, starts a fresh reconciliation generation with a new pre-enumeration anchor. Existing originals use minimal metadata reads instead of downloading raw MIME again. Provider removal clears live memberships but retains originals, projections, local drafts and action records. Live progress excludes remote-absent messages; `removed` counts known remote absences and `retained` counts those with a retained published original, across all generations. Each metadata snapshot/event carries its provider history ID so older deltas cannot overwrite newer membership state. Completion means the currently represented changes have completed storage/projection; it does not promise a mailbox will remain unchanged between polls.

Provider contracts: [Google synchronization guide](https://developers.google.com/workspace/gmail/api/guides/sync), [history pagination and expiration](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list), and [profile history anchor](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile). Validation uses synthetic provider responses and encrypted local databases; no live mailbox was accessed.
