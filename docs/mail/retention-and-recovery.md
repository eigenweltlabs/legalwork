# Mail retention and encrypted recovery (EIG-151)

Settings → Mail accounts → Retention and encrypted recovery is the complete local workflow. The default is indefinite retention. A per-account number of days supplies the cutoff for **manual** cleanup of provider-deleted copies; saving a number does not schedule deletion. This deliberately replaces the initial proposed automatic 30-day window in `scope.md`. No firm-policy engine or legal retention guarantee is claimed.

## Deletion scopes and references

Provider deletion changes mirror membership/tombstones and leaves downloaded bytes. Disconnect stops network work, removes usable local credentials, and locks provider-backed mail until explicit reconnect. Disconnect does not itself delete provider mail, revoke all provider sessions, or remove the local archive. Export/backup can be chosen before explicit local removal.

The Settings preview shows selected message count, deletable content references/bytes, protected references and matter-retained records. Account removal also states the draft and submission-history counts, including accepted and uncertain evidence. Applying requires the exact phrase `DELETE LOCAL COPIES`, pauses background Mail, and leaves it paused. Nothing is sent to a provider by purge. Connected mirrors can download again when sync resumes.

- **Provider-deleted copies past the configured age:** tombstone observation time, not message date, determines eligibility.
- **All local mirror messages:** selected account only. Retained originals, draft attachment pins and submission evidence remain.
- **Disconnected account and local history:** removes that account's local records and explicitly disclosed draft/submission history. Connected accounts, active work, shared children, matter-retained snapshots and unfinished file jobs block removal.

Offline archives are excluded unless explicitly selected. Selection does not override retained references. A stopped file job can be deliberately abandoned by typing `ABANDON CHECKPOINT`: only checkpoint/snapshot bookkeeping is removed. Imported messages and exported files remain. A preparing or running executor blocks abandonment and purge. Exported files are never silently removed.

The worker holds previews for ten minutes; restart invalidates them. A preview simulates the exact SQL deletion inside a rolled-back savepoint. Apply recomputes selected keys, byte hashes, account credential generation, settings, history and blockers inside the same transaction, then rejects a changed preview. Foreign keys and the final foreign-key check protect refs; deletion failure rolls back message/ref/publication/chunk changes together. Mirror cleanup only collects refs belonging to the selected messages, not arbitrary orphaned account content. Draft and matter pins remain authoritative. Unfinished portability entry refs are explicitly protected despite not having a SQL foreign key.

Matter snapshots/parts and local receipts are covered; external files in any connected file-storage destination are independent copies with separate authorization, storage and retention. A local purge or backup neither deletes nor backs up those external files. Matter pins can leave an account retained; the UI does not claim it was fully deleted.

These operations remove records from the **active generation**. Earlier encrypted generations, separate backups, exports and OS copies remain. SQLite deletion, key rotation and ordinary file deletion do not guarantee physical erasure on SSDs, snapshots or backup media. There is no automatic destruction of old generation keys.

## Backup and clean-profile restore

The existing EIG-126 native maintenance barrier stops the worker and all network/file runners, copies a consistent encrypted SQLite database containing the blob chunks, validates SQLite and foreign keys, reads every published ref through its SHA-256 check, validates retained-part hashes and the persisted retained manifest hash, and checkpoints/fsyncs the result. A missing publication/chunk, wrong hash or corrupt database fails the operation. There is no provider download to fill missing parts.

New `recovery.json` envelopes are **version 2**, with authenticated ciphertext SHA-256, schema version, creation time and a complete verified inventory. Counts include accounts/messages/refs/bytes and retained snapshots/parts; the inventory also reports manifest parts that were not stored. Incomplete provider downloads are disclosed, not claimed as backed up. Existing **version 1** envelopes remain supported and undergo current deep validation; they have no historical inventory to compare. Tests use the original schema 8 from EIG-126 commit `deb529c8c`, and schema 24 immediately preceding this feature.

The envelope wraps the database key with AES-256-GCM and scrypt (N=32768, r=8, p=1), following EIG-126. The desktop native folder chooser supplies paths. HTTP accepts a passphrase only; keys, secrets and native paths are never returned to the renderer. Passphrase inputs are cleared after submission. Keep a strong unique recovery passphrase separately: there is no vendor reset. Existing POSIX permissions, Windows ACL handling, OS safeStorage custody, physical child reaping and atomic generation-pointer promotion remain in force. The private worker has a 20-minute bound; a dataset that cannot verify in that interval fails safely rather than publishing a partial backup. Maintenance has no renderer auto-timeout: keep the page open or explicitly cancel. Leaving the page or losing the HTTP connection aborts the service controller and physically kills/reaps the worker before its storage barrier can reopen. Native folder selection remains user-controlled; cancellation is rechecked before starting work. The Node server’s keep-alive timeout does not limit an active maintenance request. No 100k timing claim is made by this change.

Restore copies the source into a fresh candidate, migrates it, uses a fresh OS-wrapped key, validates counts/hashes against v2 inventory, and rebuilds local search in bounded batches **without provider credentials or network access**. A clean profile with the same trusted local owner can restore it. Archive accounts remain readable/searchable offline. Provider accounts require explicit reconnect. Wrong key/passphrase, damaged database or missing blobs cannot promote a candidate. The backup source is never modified. A damaged current database can be recovered because restore does not need to open it. Failure after the atomic pointer rename can have an uncertain acknowledgment: inspect the selected generation on reopening. Previous generations and failed candidates are retained.

## No replay after recovery

Restore removes OAuth/IMAP usable secrets and SMTP configuration/passwords; shared bindings are disconnected with fresh generations. It pauses provider runs, clears stale leases, and resets notification/event epochs. Queued/running/dispatching/retry actions become uncertain; **accepted submissions stay accepted**, with their evidence intact. All restored submission IDs receive a durable quarantine marker. Even after reconnect, old records cannot retry, submit, append Sent copies or run accepted-send remote draft cleanup. Inspect the provider and create a new draft deliberately if a new submission is needed.

Restored provider-draft mappings are disabled and quarantined; their local content remains. Save a local copy to create a fresh mapping after reconnect. All restored file-job IDs are quarantined; a fresh native file selection starts a new import/export. Existing archive messages remain usable. Filing queued/uploading jobs become uncertain with `restore_review`, and all receipt IDs are marked for EIG-148's fresh-authorization fence. Reconnect alone grants no permission to republish, clean up drafts, or resume filesystem operations. Future agent-access grants must be revoked during restore before integration. The trusted synchronous `quarantineRestoredMail(db)` function is the restore extension point for schema26 connected-storage receipts: preserve accepted/uncertain evidence, move in-flight saves to uncertain, and mark every receipt using kind `filing` with entity ID `storage-save:<receipt-id>`. The provider runner must check `isRestoredMailWork` before any upload, retry or delete. Reconnect cannot clear the marker; a fresh deliberate save creates a new receipt. EIG-148 owns this schema26 integration and retains snapshot pins.
