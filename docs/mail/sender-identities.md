# Sender identities, aliases and signatures (EIG-145)

Mail stores sender choices separately from editable draft headers. Settings → Mail accounts → Sender identities and signatures lists permitted choices, local plain-text signatures, and independent defaults for new messages and replies. Existing connected accounts with no stored identities perform authenticated read-only discovery when first opened. The composer offers a picker; an old draft with a missing or unavailable identity remains locally recoverable and requires a current choice before publication or sending. The selected identity and inserted signature snapshot survive local draft recovery. Switching identities replaces only an unchanged signature previously inserted by the editor; edited message text is preserved. Rich signatures escape markup. Sanitization retains the internal signature marker, and plain-to-rich conversion marks only an unchanged inserted suffix, so normal editing and mode changes do not duplicate signatures.

## Provider contracts

- Gmail: authenticated `users.settings.sendAs.list` discovers the primary address and custom aliases with `verificationStatus=accepted`. Pending or missing verification on a custom alias is excluded. The existing `gmail.modify` grant supports this read. Users add and verify aliases in Gmail Settings, then refresh in LegalWork. Local signatures are independent of Gmail's HTML signature setting; provider HTML is not imported. [Google sendAs list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.sendAs/list), [sendAs resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.sendAs).
- Microsoft: the authenticated `/me` address is a self identity. Shared/delegated choices inherit EIG-132's separately configured mailbox and explicit administrator-confirmed Send As / Send on Behalf declaration plus `Mail.Send.Shared`. Graph does not enumerate authoritative Exchange sender grants; `proxyAddresses` is not used as send authorization. Exchange checks actual rights at submission. [Microsoft send from another user](https://learn.microsoft.com/en-us/graph/outlook-send-mail-from-other-user).
- IMAP: no sender is inferred from the login name. Users explicitly confirm outgoing-provider permission for each SMTP address; these records are labeled **user-confirmed**, never provider verified. Settings supports adding and removing them. SMTP acceptance is still required, and SMTP configuration/submission belongs to EIG-146.

## Persistence and publication

Encrypted schema 20 adds `mail_sender_identities` after the draft (18) and search (19) migrations. `SenderIdentityRepository` binds identity records to an account and credential generation, with stable IDs derived from account plus address. Refresh replaces the complete provider set atomically while preserving local signatures and defaults by address. Removed aliases remain visible as unavailable for recovery. Failed authenticated refresh leaves the prior set unavailable. Disconnect, archive lock, changed generation or missing sender scope disables choices. Shared identity availability derives from current parent access and mailbox permission every time.

`mailDraftContentSchema` carries nullable `senderIdentityId` and `senderSignature` (inserted plain-text signature snapshot); legacy content receives null/empty defaults. Local draft saves retain unavailable/legacy senders, so editing is never lost merely because permissions changed. `SenderIdentityRepository.assertSender(accountId, content)` requires the current identity ID and matching From address before a submission is enqueued and before remote draft publication. `buildMailMime` must receive only the resolved identity address in `authorizedSenders`, never a list built from draft From text. Adopting a remote draft maps its From only to an available stored identity; unknown sender text remains recoverable without authorization. Outbox execution must resolve again immediately before dispatch and respect provider permission failures; enqueue-time validation is not permanent authorization.

The private worker API exposes list, refresh, settings, and explicit IMAP configuration through authenticated `/mail/v1/accounts/:accountId/senders` routes. Provider tokens, SMTP secrets and arbitrary endpoints are never renderer inputs or results.

## Focused evidence and final gate

Native encrypted-store tests cover accepted/pending Gmail discovery, alias removal, generation/disconnect fences, owner isolation, forged From rejection, shared permission/parent-lock revocation, explicit IMAP configuration and removal. Composer model tests cover defaults, persisted identity and signature recovery, text preservation, and escaping. Isolated hidden Electron renderer probes cover Settings saving and selecting aliases without an arbitrary From field, plus the existing shared-mailbox permission UI.

Actual Gmail alias delivery, Exchange Send As / Send on Behalf and resulting Sent Items location, SMTP acceptance, and real-provider revocation are the final EIG-173 provider-account gate after the EIG-146 outbox. No live account, send, or whole-app/platform certification is claimed here.
