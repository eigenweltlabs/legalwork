# Local drafts, durable intents and events

EIG-123 exposes host-only POST JSON operations under `/mail/v1/accounts/:accountId`:

- `drafts/save`, `drafts/read`, `drafts/delete`, `drafts/query`, `drafts/attachment`.
- `actions/submission`, `actions/mutation`, `actions/read`, `actions/query`, `actions/cancel`.
- `events/query`.

The strict request/result schemas in `local-view.ts` are the API contract. Every operation checks owner/account scope before reading rows or counts, rejects disconnected archives, and uses the service's lock/disconnect epoch fence. Responses are private, no-store and bounded by the worker frame limit. Lists retain the last returned key when trimmed; an individually oversized record returns `response_too_large` without advancing a cursor.

Draft saves use a caller UUID and expected `{generation,revision}` (null for creation). Saves retain immutable full snapshots in encrypted SQLite. CAS conflicts return 409; an identical immediately repeated save is idempotent. Logical deletion hides the head without deleting revisions or cancelling a queued intent. Explicit version reads remain available. Combined draft JSON is capped at 24 KiB; address arrays and header fields are validated and HTML is inert data, never rendered here. Attachments select existing account-owned published attachment references, not uploads or arbitrary blobs. `drafts/attachment` binds the exact draft version, ordinal and reference ID, allowing bounded reads even after a provider changes the original manifest.

Submission intents pin an immutable draft revision and its attachment references. Mutation intents describe read-state or folder/label changes with an explicit provider precondition. Neither executes a provider call or changes local observed message state. `queued` means durable intent, never sent; `executionSupported:false` is explicit. Replay keys identify the exact original intent across draft edits/deletion and credential changes. Reusing a key for different input conflicts. A new intent captures the current connected credential generation; status exposes only whether it is still current. Payloads and credentials are absent from status/list/events. There is no API to claim, dispatch or reconcile actions. Cancellation uses journal CAS and preserves dispatch uncertainty.

Events are durable metadata-only change hints for messages, provider presence/tombstones, memberships, published content/projections, drafts and action status. Gmail scan-generation-only updates do not emit hints. Poll with `{stream,after,limit}`; initial `{}` obtains the account's independent stream and sequence. Multiple hints may describe one transaction; consumers refresh the referenced typed view rather than interpreting hints as provider outcomes. No automatic retention/pruning is implemented. Restore must call `resetMailLocalEventStreams(database)` in its quarantine transaction: an old stream then returns `resetRequired:true`, no rows, and a new stream/current cursor. The consumer resnapshots authorized views and resumes from that cursor, preventing silent skips after restored sequence rewind. Existing immutable versions, pins and events survive recovery.

Schema v10 is additive after actual Graph v9. Legacy reserved `mail_drafts`/`mail_actions` remain untouched. Foreign keys retain draft attachment and action revision references. Triggers append hints atomically with source mutations; rolled-back work emits no committed event.

Acceptance uses synthetic fixtures only: actual encrypted Node storage checks CAS/reopen, unchanged originals, DB/WAL plaintext-marker absence, immutable submission replay, retained attachment reads, scope/disconnect fences, uncertain cancellation, event rollback/reset and interrupted migration. A real loopback HTTP→service→Node-worker test covers saves, historical reads, duplicate submissions, conflict, event continuation, lock and restart. Provider sending, uploads/composer UI, alias authorization, remote draft synchronization and event streaming transports remain separate work.
