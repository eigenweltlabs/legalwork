# Internal account access coordinator

`MailAccessCoordinator` accepts the keyed database, trusted owner ID, and a trusted `loadProviderSettings(binding)` callback. Engine callers use `acquire(accountId)` to receive `{accessToken,expiresAt,grantedScopes,version}`. This is deliberately an internal secret-bearing interface: it is not a worker command, HTTP response, generic account listing or log object. `close()` aborts pending work immediately and prevents future acquisition; it does not close the database it borrows.

The repository's `getBinding(accountId)` is an owner-checked single-account lookup of immutable provider/client/authority/provider-subject fields. Acquisition captures the connected generation and revision before asynchronous configuration loading. Provider/client/authority must match the immutable binding; Graph GUID configuration is normalized. The subject remains the stored identity established during connection, never an email address or settings value.

One acquisition promise is shared per account, with up to 64 accounts in flight. Cached access must outlive the default 60-second margin (configurable 0–300 seconds). Otherwise, one refresh attempt runs with the existing transport. The total acquisition deadline bounds configuration and refresh together (default 30 seconds, configurable 10 milliseconds–60 seconds), including injected implementations that ignore abort. Late continuations check the signal, absolute monotonic deadline, and exact persisted version before writes or token return. The monotonic check also rejects synchronous overruns when the event loop has not yet delivered the timer. Close, disconnect and reconnect therefore fence pending work; explicit generation/revision conflicts return `stale_credentials` without retrying or clobbering a winner. Callers can acquire again to read the winner.

Refresh token preservation/replacement follows the transport's explicit action. Current `grantedScopes:null` remains null in SQLite and the returned access result, even if earlier grants were known. Explicit refresh scopes replace the prior current list. Neither requested configuration nor historical grants are substituted as current proof. Callers must gate their requested operation on the result; this coordinator does not claim a mailbox permission check or a completed sync. Refreshed tokens need to be unexpired; the margin is the proactive refresh threshold for cached access, not a minimum provider token lifetime.

Errors contain fixed codes and no underlying messages, payloads or causes. `retryable` classifies timeout/transient/rate-limit/conflict/capacity failures; `reconsentRequired` identifies missing refresh credentials or provider-required consent. Safe nonnegative integer provider retry advice is preserved without shortening the requested delay; invalid advice becomes null. A future scheduler must use bounded wakeups without retrying before that delay. There are no automatic retry loops, schedulers or automatic disconnects for provider failures.

## Validation

`pnpm --dir apps/server exec bun test src/mail/providers/access-coordinator.test.ts` compiles the production sources and runs the `.node-test.mjs` suite in actual Node against Multiple Ciphers encrypted SQLite. Synthetic cases cover account isolation, binding mismatch before HTTP, cached/margin behavior, refresh deduplication, token/grant preserve/replace, encrypted DB/WAL marker scans, reopen, settings/network lifecycle fences, close and deadline against uncooperative work, and competing rotations. One case uses the real refresh response parser with an injected HTTP response. No test contacts a provider or uses real credentials. `pnpm --dir apps/server exec tsc --noEmit` checks server types.

The coordinator has not yet been wired into sync, worker shutdown, or public APIs. A returned token is a point-in-time capability, not a revocable object: callers must stop outstanding provider work when their engine lifecycle closes. Persistence fences cannot revoke tokens already handed to a caller or invalidate a remote provider session.
