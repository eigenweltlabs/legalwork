# Mail account onboarding — EIG-135 / EIG-120

Current live evidence and remaining account requirements: [EIG-173 qualification](live-provider-qualification.md).

The Mail section in app Settings connects Google, personal Outlook/Hotmail, the configured Microsoft organizational tenant, iCloud, and manual direct-TLS IMAP. Mail opens through the local OS keychain automatically; there is no user-facing mail lock control. Provider passwords and OAuth tokens are never copied into renderer storage. Google/Microsoft sign-in opens the system browser; the existing loopback state/S256 flow, authenticated identity discovery and atomic credential repository perform connection. Setup polls fixed status fields, supports cancellation and explicit reconnect, and explains missing permission/identity errors. Folder selection is optional for IMAP. Successful connections start eligible sync automatically. Connected sessions resume after reopen unless explicitly paused.

Microsoft uses two explicit authorities. Organizational accounts retain the configured tenant GUID and authenticated `/organization` tenant check. Personal accounts use only `consumers` authorize/token endpoints and authenticated Graph `/me` with User.Read, because `/organization` does not support personal accounts. Personal Graph IDs are bounded opaque strings, not GUIDs or email/UPN. Canonical authority+subject is retained in encrypted credentials; refresh configuration and the worker cache include authority, separating personal and organizational accounts with the same client ID. No unverified JWT or email-domain inference selects an identity. `common`, `organizations` and arbitrary authorities remain rejected. The HTTP client can choose personal vs organizational; it cannot supply client IDs, tenant IDs or endpoint URLs. [Microsoft authorization authorities](https://learn.microsoft.com/en-us/graph/auth-v2-user), [Graph user access](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0), [organization access](https://learn.microsoft.com/en-us/graph/api/organization-get?view=graph-rest-1.0).

iCloud uses `imap.mail.me.com:993`, verified TLS and an app-specific password entered locally. Apple requires two-factor authentication to generate that password; its documented IMAP username is normally the local email portion, with full email as fallback. Manual IMAP supports direct TLS and validated server certificates; insecure connections and STARTTLS are intentionally unavailable. IMAP retrieval requires implicit TLS. SMTP and durable outbound submission are configured separately in Settings; see the outbox documentation. [Apple server settings](https://support.apple.com/en-us/102525), [app-specific passwords](https://support.apple.com/en-us/102654).

IMAP requests carry a generated cancellation ID outside account settings. The worker retains bounded ten-minute request records, rejecting delayed/replayed cancelled starts. Cancellation aborts and closes the active matching transport while retaining its physical slot until settlement; it cannot cancel another request ID. Disconnect keeps original account identity/archive data and enforces existing credential fences. JavaScript cannot guarantee physical erasure of immutable strings; password fields are cleared on submit/cancel/close, never logged or persisted in browser storage, and sent only to the literal authenticated loopback API.

Focused verification combines actual isolated Electron form interactions, host-token HTTP forwarding/rejection, real encrypted Node OAuth/refresh/reopen and IMAP cancellation tests. No live credentials, provider traffic, broad platform suite or whole-app build is used for these tests.

Reconnect selects Graph personal/organizational authority from the encrypted existing binding, including disconnected accounts; a caller cannot silently switch it with a `personal` flag. Account lists expose only an optional non-secret `personal` boolean for that selection. The existing immutable client/subject binding and publication CAS still apply.
