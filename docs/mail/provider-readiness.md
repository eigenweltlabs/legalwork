# Mail provider readiness (EIG-120)

Reviewed 9 September 2026 against official documentation and baseline `c4b338e85`. This is engineering prerequisite work, not a verified connection to either provider. No registration console, credentials, real mailbox, consent flow, or sending was accessed.

## Current application boundary

`apps/server/src/extensions/google-workspace.ts` already owns Google Workspace configuration, encrypted account storage, refresh/exchange, and a five-minute connection flow. It binds `127.0.0.1` on an OS-assigned port, uses `http://127.0.0.1:<port>/`, random state, S256 PKCE and system-browser authorization. `apps/server/src/routes/core.ts` exposes the existing connection flow. There is no built-in OAuth client ID/secret; operators supply `LEGALWORK_GOOGLE_WORKSPACE_OAUTH_CLIENT_ID` (legacy `GOOGLE_WORKSPACE_OAUTH_CLIENT_ID`) and `GOOGLE_WORKSPACE_OAUTH_CLIENT_SECRET` (legacy `LEGALWORK_GOOGLE_WORKSPACE_OAUTH_CLIENT_SECRET`). An optional token broker is a separate existing path.

The optional `gmailRead` feature requests **gmail.readonly plus gmail.compose**, not gmail.modify. Full mail must introduce an explicit scope upgrade and new consent, then check actual returned grants before enabling operations. Existing permission guards must be reviewed for accepting modify; do not silently interpret an old connection as full mail authorization. No existing OAuth code is changed here. Its comment claiming every Gmail scope is restricted and write-capable is inaccurate: readonly cannot write, and send is sensitive rather than restricted. [Google scope table](https://developers.google.com/workspace/gmail/api/auth/scopes).

## Gmail registration and authorization

1. Use an operator-owned Google Cloud project; enable Gmail API. Configure Google Auth Platform branding, audience, data access and support/contact information. For an external testing app, add each dedicated tester under Audience → Test users. Internal audience is appropriate only for the owning Workspace organization. [Consent setup](https://developers.google.com/workspace/guides/configure-oauth-consent).
2. Create an OAuth **Desktop app** client. Keep the downloaded installed-client configuration outside source control. Desktop credentials cannot be confidential; never use their secret as proof of app identity. Use authorization code flow in the system browser, with fresh random state and a fresh 43–128-character verifier, S256 challenge, and exact verifier/redirect reuse at token exchange. Bind the callback only to loopback, on an OS-assigned port. The implementation target remains `http://127.0.0.1:<actual-port>/`; Google also supports `[::1]` for desktop. This is not a hosted-server callback. [Installed-app OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).
3. Request `https://www.googleapis.com/auth/gmail.modify` for reading, drafts, sending, labels/read state, archiving and trash. It excludes immediate permanent deletion; do not request `https://mail.google.com/` for this client. Also request `openid` and `email` for stable Google subject discovery and verified email consistency with the Gmail profile; see [identity contract](provider-identity.md). Restricted-scope verification applies to public use; storing/transmitting restricted data on servers can also require a security assessment. Confirm applicable exceptions and deployment data handling with the operator before production distribution. [Scope definitions and verification](https://developers.google.com/workspace/gmail/api/auth/scopes).
4. Obtain offline access and handle refresh revocation/expiry as reconnect-required. External apps in Testing receive seven-day refresh tokens for Gmail scopes, so a week-long sync test must expect reauthorization. [Google token expiration](https://developers.google.com/identity/protocols/oauth2).

Use `https://accounts.google.com/o/oauth2/v2/auth` and `https://oauth2.googleapis.com/token`; these endpoints and the Desktop exchange are documented in [Google's installed flow](https://developers.google.com/identity/protocols/oauth2/native-app). The readiness helper models the existing direct-exchange requirement via `clientSecretConfigured`; it never receives the secret and does not assess the token-broker path.

## Microsoft Graph registration and authorization

1. In the dedicated Microsoft Entra test tenant, create an app registration with **Accounts in this organizational directory only**. Record Application (client) ID and Directory (tenant) ID. Configure **Mobile and desktop applications**, not Web or SPA. This first pilot uses an explicit tenant GUID; consumer, common, organizations, domain-name and multitenant authorities require a later intentional audience policy. [Registration](https://learn.microsoft.com/en-us/graph/auth-register-app-v2), [account types](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app).
2. Register `http://localhost/mail/callback` for a simple desktop test and listen only on loopback, using `http://localhost:<actual-port>/mail/callback`. Microsoft ignores the port for localhost matching, but preserves the path and its case. Alternatively register the exact `http://127.0.0.1:<chosen-port>/mail/callback` through the manifest as a native redirect; do not assume its port is ignored. Microsoft currently does not support `[::1]`. Avoid multiple registrations differing only by localhost port. [Redirect rules](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url).
3. Add Microsoft Graph **delegated** `User.Read`, `Mail.ReadWrite`, `Mail.Send`, plus `openid profile offline_access` in authorization requests. User.Read supports account identity lookup. Mail.ReadWrite does not send; Mail.Send is separate. No application permissions, client credentials, shared-mailbox permissions, or domain-wide access are required for the signed-in user's mailbox. Delegated mail scopes are marked as not requiring admin consent by default, but tenant user-consent policy can still require administrator approval. [Permission reference](https://learn.microsoft.com/en-us/graph/permissions-reference), [consent policy](https://learn.microsoft.com/en-us/entra/identity-platform/consent-types-developer).
4. Use `https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/authorize` and `/token`, authorization code with S256 PKCE and random state. A public desktop client must not ship a client secret. Request offline_access for refresh; persist replacement refresh tokens securely. This is an interactive code flow; do not enable ROPC, implicit flow or device-code flow as a workaround. [Microsoft authorization code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).

## Configuration helper contract

`apps/server/src/mail/provider-config.ts` is a pure, typed prerequisite check with no environment reads, network, tokens or account access. Call it with explicit settings, including a runtime callback and (Graph) operator-declared registered callback. It checks client ID shape, desktop/S256 declarations, loopback safety, required requested scopes, and the pilot tenant/redirect policy. `configurationReady` means only those declarations pass local validation; `authorization` always remains `not_checked`. Output contains fixed issue codes, never supplied values. It does not verify that the registration exists, consent is granted, API enabled, callback listener bound, or mailbox provisioned. It is not yet wired to routes or existing OAuth. Extra requested scopes are not prohibited by this helper and require separate least-privilege review. Runtime JSON must be parsed/validated before calling the typed helper.

## Test accounts and evidence required before live acceptance

- Gmail: dedicated Workspace test user with Gmail enabled, test-app access permitted by Workspace policy, and access to the project/client registration owner. Use a second controlled mailbox as recipient. Verify consent-screen test membership and document Internal/External plus Testing/Production status without recording credentials.
- Graph: dedicated tenant, registration owner/admin contact, an Exchange Online mailbox provisioned for the test user, appropriate mailbox license/service enablement, and a second controlled recipient. An Entra identity alone does not demonstrate a working mailbox. Obtain approval for the requested delegated scopes under tenant policy and ensure MFA/Conditional Access permits interactive desktop sign-in.
- Seed only synthetic mail: inbound/outbound threads, drafts, labels/folders, read/unread, attachments and non-ASCII content. Agree exact sender/recipient addresses and authorization for test sends before executing them. Never use client matter data for initial acceptance.
- Capture redacted evidence for successful sign-in, denied/partial consent, actual returned scope checks, offline refresh after restart, revoked refresh requiring reconnection, account identity/tenant isolation, and cancellation/state mismatch. Then verify provider reads, draft creation, read-state/archive/trash and controlled sending in a separate authorized integration test.
- Readiness remains **live authorization untested for both providers**. Configuration tests do not validate provider interoperability, production verification, real token storage/refresh, or UI behavior. The lead should obtain operator-owned registrations and test mailboxes, then implement the scope upgrade and separate Graph OAuth adapter against these prerequisites.
