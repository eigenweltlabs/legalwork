# CI and execution efficiency

## Pipeline changes

- Unit tests and real-engine integration run independently after their own prerequisites. The existing two required `legalwork-tests` names aggregate all selected checks, including failures and cancellations. These metadata gates use Linux runners so they do not wait for a second Mac slot after native testing finishes. Presentation-only changes skip engine jobs entirely instead of scheduling an empty Mac integration job.
- PR jobs prepare one guest image per CPU architecture. Four native-only consumers prepare and validate their own runtime after their guest architecture. Linux engine runtime preparation overlaps compilation, then the engine job downloads and validates that exact same-run archive. The Mac engine prepares its runtime in its existing job, avoiding an additional ARM Mac runner allocation. Mac/Linux engine jobs retain protected-engine assertions and reuse their server build. Linux x64 integration uses Ubuntu 24.04, matching the native producer and warmer rather than following the moving `ubuntu-latest` image. Manual package diagnostics retain the shared producer/archive path. Both required check names and the final result await both guests and all six native validations.
- PR Electron renderer assets build once on Linux. Mac unit jobs verify the exact source, version, build settings and file hashes before running the actual Electron assertions. Runtime-only validation installs the server dependency closure with native lifecycle scripts enabled; worker preparation and help generation resolve their declared dependencies from that closure.
- A failed Windows MSYS2 bootstrap gets one fresh-install retry, including the full system upgrade. Checksum-pinned QEMU packages and signature checks still run afterward; test failures are not retried.
- Guest and native QEMU bundles use exact source, host-image, Node version and architecture cache keys. Native build commands live in a separately hashed build action so scheduling or validation edits do not invalidate compiled QEMU bytes. Hits verify all file hashes and the runtime manifest, then still execute the selected isolation tests. The dedicated `dev` warmer builds without installing the application workspace. It runs nightly as well as on source changes, so host-image/toolchain key changes are warmed before daytime CI; it skips native artifact publication and keeps same-run guest artifacts for one day. The trusted `dev` warmer seeds the shared default-branch cache; branch and PR saves remain isolated by [GitHub cache scope](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache).
- A single alpha workflow produces one fresh, signed production engine for macOS and both Windows architectures. The [concurrency group](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) retains one active alpha and the newest pending alpha. The Windows-only manual diagnostic remains available.
- Release and alpha renderer and Office assets build once on Linux in parallel with the native runtime and engine producers. CI package acceptance also shares one portable build across its native matrix. Native jobs verify the source commit, version, Vite environment and every portable output before building their server and platform resources. Signing, native-module tests and packaged-startup tests remain platform-specific.
- Full-workspace pnpm store keys are shared by OS, architecture and lockfile across workflows. Filtered installs have a separate job-owned store and cache namespace including the filter, lifecycle mode, Node ABI, OS, architecture and lockfile; they save that filtered closure immediately after installation and cannot restore or populate the full-workspace/legacy Electron cache. The install action can disable store reuse for a fresh-install comparison. PR Windows ARM64 validation uses a fresh isolated store because hosted cache restoration plus installation was slower than a fresh install; other filtered consumers retain their scoped caches. UI-MCP syntax/packing checks need no installation; DOCX checks install only the app dependency graph. Filtered installs cannot seed an incomplete full-workspace cache. Complete-store saves happen immediately after installation within the run’s cache scope. Native engine consumers download an OS family rather than twelve archives; the full distribution remains available for universal publication.
- Engine compilation on a cache miss uses two independent staging workers. Production can reuse an exact retained production artifact with an independent producer-log manifest pin and full archive/provenance/signature verification. Its separate fingerprint excludes ordinary app commits/versions and rejects development/PR cache promotion. Failures stop new work and wait for in-flight builds. Production provenance, twelve-target coverage and required signatures remain enforced.
- Test, engine-target, desktop build, notarization-archive, notary submission and stapling spans are retained with workflow artifacts. Notary submission includes Apple's upload and processing time; it is not an upload-only measurement.
- Linux release tarballs use gzip level 6 rather than electron-builder's default level 9. A manual nonpublishing alpha benchmark builds each Linux app once, then measures both archive levels on those exact bytes, verifying every file hash, link and mode and reporting the size difference. AppImage configuration is unchanged.
- Manual alpha `signing_test` runs can compare `serial-full-ui` (one engine worker and per-platform frontend builds) with `optimized` (two engine workers and verified shared frontend assets) on one commit and an identical `benchmark_version`. These controls require publishing to be disabled. The serial control still uses the improved source staging and one shared producer, so it measures those selected execution/scheduling differences rather than reproducing the entire historical pair of alpha workflows. Optional `linux_benchmark` adds x64 and ARM64 archive comparisons. Failed startup checks retain redacted diagnostics without changing their assertions or deadlines.

### Native runtime recovery within the 10GB cache limit

Cold Mac QEMU builds select the shipped emulator target rather than the default target, which also compiles upstream unit/qtest programs that are never executed by the packaging job. Meson then performs the normal installation without rebuilding unrelated targets, preserving installed executables, firmware, libraries and metadata. This changes the exact native build key. LegalWork's native QEMU execution, macOS compatibility and selected real VM/isolation/networking checks still validate the resulting runtime; the hosted cold Intel lane supplies validation and timing evidence.

Actions-cache eviction no longer requires rebuilding an unchanged native runtime if its normal same-run delivery artifact is still retained. Native delivery artifact names include the complete build key, allowing a direct exact-name lookup without scanning unrelated historical builds. On an exact cache miss, the preparer searches eligible completed runs for that indexed native artifact and requires a successful native producer step, the exact current source/host/toolchain key in its log, and agreement between the independent upload digest and GitHub artifact metadata. Downloaded ZIP bytes must match that digest before extraction. Extraction rejects links, traversal, duplicate entries and extra archives; the current receipt, manifest, file hashes, QEMU execution and selected native isolation checks still run. For migration, legacy unindexed delivery artifacts have a bounded best-effort lookup (the latest ten artifacts, at most three eligible producers); new indexed artifacts retain full pagination. A changed build key, missing proof or expired artifact follows the original pinned-source build path. Corrupt selected bytes fail.

PR recovery accepts the same repository/PR/branch or trusted production sources; production cannot consume PR artifacts or another benchmark branch. Recovery reuses already-retained native delivery artifacts and does not increase their retention or create another artifact class. The repository cache limit remains 10GB. In the preserved failed trial `42033069108`, an unchanged Mac runtime key had been evicted and native QEMU compilation alone cost about 7m40s; its retained artifact remains independently pinned for the eviction-recovery benchmark.

### Native packaging preparation

Production engine cache hits still download the complete distribution and verify all twelve archives, provenance and native Apple signatures against current source policy. After that gate, consumers can download the original producer's retained full/OS-family delivery artifacts directly. The producer exports that run ID alongside the independent manifest pin, and every native consumer still verifies its archives. Four duplicate uploads are skipped only when all original delivery artifacts are unambiguous and remain retained for at least another hour. Missing, expiring or unavailable metadata selects fresh current-run delivery uploads; retention and storage limits do not increase. Development handoffs keep their existing current-run uploads.

The combined Mac/Windows alpha prepares and verifies the Mac runtime inside its existing Mac packaging allocation. The shared runtime matrix contains Windows and optional Linux targets, so Windows cannot wait for a Mac runtime runner. The Mac host retains native QEMU execution, exact-key verification, cache recovery and optional manual isolation tests, and publishes the same indexed runtime artifact for future eviction recovery. This removes one Mac allocation, not the need to verify or compile a changed runtime.

The read-only `ci-windows-packaging-benchmark.yml` workflow compares the actual differential NSIS payload archiver on the last measured signed installers. It runs level 9/5 and then 5/9 on each native Windows architecture, with the existing 1MB dictionary, nonsolid blocks and install-time-decodable BCJ filter. Every extracted file hash must match the identical input. It needs no signing credentials or release writes; these measurements are separate from a fresh full alpha benchmark. Paired hosted run `42255869886` verified 2,800 x64 and 2,796 ARM payload files: x64 mean146.804s →128.688s (12.34% faster, +0.37% bytes); ARM mean162.183s →136.867s (15.61% faster, +0.41% bytes). Windows alpha and stable packaging therefore select level5. The dictionary, nonsolid blocks, BCJ filter, signing and updater behavior remain unchanged.

Mac and Windows native packaging install the desktop, orchestrator and Actaport workspace dependency closures, including the server and their other workspace dependencies. The shared renderer/Office producer owns frontend dependencies. The filters are passed separately to pnpm, retain native lifecycle scripts, and use an isolated store; a filtered install never populates a full-workspace cache. Mac and Windows x64 cache that store. Windows ARM uses a fresh scoped store: the actual 329MB cache hit in alpha `42033069108` spent about 1m31s restoring plus 3m22s installing, whereas the preparation-only fresh scoped install took 2m57s. The compiled speech cache remains enabled. The serial/full-UI diagnostic selects the whole workspace. This replaces the Windows ARM alpha's uncached full install, which took 9m15s in full alpha `42015659494`; an older paired full-store experiment had favored a fresh install, but did not measure this smaller closure.

Windows ARM packaging prepares the pinned speech adapter once, before app building. Its cache key includes upstream/library/license pins, build scripts, registry dependency integrities/patches, Node, CMake, addon packages and the runner image/toolchain version. The key retains the dependency identity from the frozen installation across app version stamping: the later lockfile-only resync can refresh unrelated registry metadata without changing installed packages. Build source, actual installed tool versions and host identity are still checked again. An offline regression executes the real release-stamping script and pnpm resync. Hits check the exact file set and every file hash, restore only the native adapter/DLLs/notices, and load the real addon before use. Corrupt, incomplete or mismatched caches fail; misses compile against the pinned libraries and retain output only after a successful native load. The normal Electron build repeats the verified load, rather than compiling again. GitHub branch/PR cache isolation still applies; this is separate from production engine artifacts.

The `ci-native-packaging-cache.yml` workflow primes the Mac/Windows x64 dependency stores and the Windows ARM speech adapter without building an app, requesting signing credentials or publishing. It runs manually, or when its own configuration changes so it can be exercised before merge. Run it on the same branch before a full nonpublishing alpha to measure cross-run cache hits; its preparation-only duration is not a whole alpha measurement. It does not add jobs to normal PR or release workflows.

Windows packaging also caches only `better-sqlite3`'s compiled Electron binary and its rebuild marker. The exact identity includes Electron version/ABI, target architecture, actual addon source hashes, packager/rebuilder versions, build settings and flags, Node, runner image, Visual Studio/MSVC and installed Windows SDK versions. A hit verifies the complete file set and hashes before copying. The regular `electron-builder install-app-deps` command still runs, allowing its normal dependency walker to prepare other or newly added native modules. Before sealing or using the addon, stock Electron must load it and successfully create, insert and query an in-memory database under the expected ABI. The preparation-only warmer performs that same rebuild/load gate. No installed dependency tree is cached, and the normal packaged startup checks still run.

Mac alpha updater ZIPs use electron-builder compression level 6, preserving its normal archive format, symlinks and signing. The temporary notarization upload uses ditto level 1 with the existing metadata/resource-fork preservation; Apple acceptance, stapling and validation remain required. A local comparison on one unchanged installed 1.7GB app measured updater level 7 → 6 at 67.7s → 26.5s (+0.59% bytes), and notary level 6 → 1 at 34.8s → 16.7s (+7.87% upload bytes). ZIPs were streamed through native bsdtar and each pair's complete uncompressed payload SHA-256 matched. These are compression measurements, not whole hosted alpha timings; runner waits and Apple processing remain part of the real full-run benchmark.

## Execution changes

The app, server and automatically discovered real-engine suites use [Bun 1.4.4 file workers](https://bun.com/docs/test/parallel). CI uses two workers for ordinary units and Mac engine files, and four for the automatically discovered Linux engine suite; native VM files remain serial. Each file retains its own globals, environment, profile and module mocks; tests within a file remain serial. Set `LEGALWORK_TEST_WORKERS=1`, `2` or `4` for comparison. No additional job or shard startup is needed. Local runs need Bun 1.4.4; `LEGALWORK_TEST_BUN_BIN` can select that executable when the shell has an older Bun. Documentation generation is checked once by the coordinator; direct Bun invocations retain the preload check.

Portable sandbox policy, path, approval and sizing tests run in the ordinary server suite. The six native targets run the explicit file list in `scripts/ci/sandbox-test-files.mjs`: VM execution and networking, the sandboxed Python calculation, and actual shell, Node transport, filesystem and link boundaries. Native files run serially against the packaged runtime and are excluded from automatic unit discovery; an explicit file argument still allows a targeted local run. Selection contracts check that every VM-gated fixture has an execution lane and exercise Bun's discovery exclusions with a failing negative control. The split retains the existing test assertions.

The released-engine startup/auth/shutdown smoke test and protected VM engine test each run in their dedicated workflow step, outside automatic engine discovery. Workflow resource integration runs in the full engine suite, with a conditional standalone step for runtime changes that do not select that suite. It is no longer invoked twice in the same job.

Linux unit runners reserve the three registered OAuth callback ports from ephemeral allocation, preserving existing reservations. Other test sockets can still use random ports without taking a callback port needed by the sign-in exhaustion checks. Managed-engine startup failures await child `close`, which follows stdio closure, so final stderr diagnostics remain available even when process exit arrives first; a held-pipe regression exercises that ordering.

Three deliberate wall-clock waits now use controlled clocks: todo-panel garbage collection and two native HTTP timeout cases. HTTP requests and responses still use actual sockets, and a negative control restoring the former ten-second timeout must fail. The sign-in regression keeps its real 10.25-second wait because that flow combines transport, query retries and timers; the fixture's idle timeout is 30 seconds in both benchmark inputs.

The recovery fixture activates its independent project contexts concurrently, and records boot, setup and teardown durations. Its readiness regression holds plugin activation until the native API reports pending, releases that barrier, then awaits readiness; it does not depend on a fixed startup sleep. It keeps separate fixture engines, databases and profiles across lifecycle cases. No cross-test engine sharing or global mock-disabling is introduced. Each native package test file runs in its own Bun process. Its temporary roots belong to a parent coordinator, which deletes them only after that process exits. Prerequisites are prepared once, and native fixtures run before heavier desktop preparation. This matches process-owned database/file-handle lifetimes on Windows; cleanup errors still fail the job, with no retries or ignored assertions. Plugin activation is awaited explicitly, and the direct temporary configuration fixture uses the engine's existing stdin lease for orderly shutdown. The coordinator records every file's outcome and continues after a failed file or cleanup so later assertions still execute.

Vitest 5.0.5 is compared with Bun on four portable files using identical assertion bodies (only the test-runner import changes). It is a diagnostic experiment, not an added production dependency or evidence about migrating the entire suite. The suite's Bun-specific servers, mocks and engine fixtures would require separate migration work.

## One-pass benchmark

Use separate checkouts of the baseline and candidate, install the frozen pnpm graph in each, generate docs, build the server and prepare the pinned Node worker before measuring. Both inputs must use Bun 1.4.4 and the same host. Apply the common sign-in fixture idle-timeout correction to the baseline. The engine binary must be independently verified and identical for both inputs.

```sh
LEGALWORK_BENCHMARK_ENGINE=/absolute/path/to/verified/opencode \
LEGALWORK_BENCHMARK_ENGINE_CACHE=/absolute/path/to/isolated/cache \
node scripts/ci/benchmark-efficiency.mjs \
  --baseline /absolute/path/to/baseline \
  --bun /absolute/path/to/bun-1.4.4 \
  --vitest-bin /absolute/path/to/vitest-5.0.5 \
  --output /absolute/path/to/results
```

Each baseline, two-worker and four-worker case runs once, sequentially. Results include wall time, child CPU, maximum child RSS, exit status and test counts. The RSS value is the largest individual child, not simultaneous process-tree memory. Dependency installation and engine compilation are excluded from these local execution measurements. A separate hosted workflow run validates the actual cross-platform orchestration and packaging; historical scheduling replays are estimates, not measured deployment speedups.

The coordinator probes both pinned Node binaries before measurement. Both inputs therefore launch their prepared native worker before a timed child-process fixture. Preserve failed samples and label any failure-driven confirmation separately.

### Development cache eviction recovery

A missing development engine cache first checks retained producers from this same repository, PR number and branch. A candidate must have a completed successful engine job, a successful full development verification step, the exact current source/cache key in its log, and one retained full distribution artifact. Its independently fetched producer-log manifest pin is checked against the downloaded manifest and receipt; the existing verifier then checks all twelve archives and provenance against the current recipe before saving or publishing same-run artifacts. A corrupt selected artifact fails the job. Discovery failure or no matching producer selects the normal source build. Forks and other branches/PRs cannot supply automatic recovery.

Production never enters this development recovery path or accepts its cache outputs. It has a separate verified production artifact cache described in [engine reuse](ci-engine-reuse.md#production-engine-reuse). Manual explicitly pinned development acceptance reuse keeps its existing behavior. The development recovery avoids recompiling unchanged reviewed source solely because another branch's caches evicted this PR's build.

In the hosted eviction experiment, the exact-key cold producer took 21m54s, including 19m50s compilation. After explicitly deleting only PR #370's engine cache, automatic recovery in run `41892388948` completed the producer in 2m58s (18m56s saved), including the independent pin and full distribution verification. The full pipeline failed in 31m03s on test failures, so this is a producer improvement, not a successful whole-CI benchmark.


Native transport fixtures run in one Bun process, followed serially by the remaining ten native files in another. Both groups retain the same preload, payloads, assertions, deadlines and one VM worker; a failure in either group fails the job, and the second group still runs after a test failure in the first. The Intel comparison measured the selected 17 MiB case at 5.184s with its source file alone versus 7.041s loaded with all eleven files. That removes measured shared-context overhead; it is not proof that the earlier timeout is eliminated.


The two multi-host Wiki API fixtures (`wiki/file-access-policy.e2e.test.ts` and `wikis-team.e2e.test.ts`) run in a fresh, isolated single-worker group after ordinary server units. Ordinary units retain two workers. Both API fixtures keep Bun's original five-second deadline and all 35 assertions; they are excluded only from the first discovery pass and required explicitly in the second. Missing fixture files fail the coordinator. Local comparison: both files passed in 1.472s with two workers versus 1.115s with one; hosted full-pipeline validation remains required. Expected-failure coordinator contracts capture their own output/timings instead of polluting the real CI timing artifact.

Model-request fixtures await the existing bounded native catalog readiness helper before inference, including newly registered locations and engine restarts. This does not retry inference or change the test deadline. Native validation records host capacity and Mac memory pressure to investigate software-emulation variability; the two Mac command failures in run `41892388948` remain failed evidence, with no proven root cause or relaxed deadlines.

The staged-command acknowledgement fixture checks response ordering with its existing blocked-engine barrier instead of racing a 100 ms scheduling timer. The original five-second test deadline remains; a negative control making acknowledgement wait for the held engine command fails at that deadline. Run `41898084042` passed all six native validations and both engine suites but failed only the old timer race, finishing in 18m53s. Keep it as failed evidence until a complete run of the revised fixture succeeds.

Explicit reload-watcher refreshes and event checks await the initial fingerprint scan. A held-scan regression reproduces the former race, where an explicit refresh returned while the background scan could still overwrite a later baseline. This fixes readiness ordering without extending the existing event/test deadlines or retrying filesystem writes.
