# OpenCode 2.1.4 plugin migration

The integration uses native `Plugin.define`, per-location tool transforms, JSON Schemas generated by Zod 4, structured `Result.output` values, native content/file parts and native permission assertions. Public tool IDs remain stable so chat cards and artifact links retain their identity. Every call resolves the invoking session's current location; the plugin setup folder does not determine project authority. Domain services remain the source of truth for project access, revisions, editor state and publication.

## Result contracts and Code Mode

Every migrated domain tool declares a truthful JSON output schema. JSON results become complete structured values without changing the original text, files or metadata. Plain text, including task source text with nonce-delimited untrusted blocks, remains an exact string. Explicit structured results retain their existing value. No data is shortened or discarded by this conversion.

Narrow schemas reuse authoritative contracts for calendar items and calculation receipts; email/calendar draft records; scheduled tasks/runs; project contents/instructions; composed skill packages/catalogs; review cards, saved reviews, libraries and corpus rows; wiki fields/data queries/documents; and complete view previews. Dynamic Office.js results, storage-provider metadata and heterogeneous service responses retain flexible JSON schemas rather than guessed field restrictions. Unknown fields are preserved.

Native Code Mode returns a child's structured `output` directly and collects its file parts. Without that value its fallback is a text string. This supports filtering and combining complete service results in one execution. It does not change the engine's policy for persisted model-visible text or make historical result files permanent. Native output schemas document the contract; the adapter does not use an output parser to strip fields.

App-state reminders are appended atomically to the admitted user prompt, with `metadata.legalworkPrompt={visibleText,reminders}` separating the user's displayed text. Topic markers support restart/revert/compaction reconciliation. Fixed system instructions stay fixed. During Code Mode, child result text is not replayed by the engine, so live state is deferred to the durable outer `execute` result; child JSON and files remain intact. Scheduling clocks are admission snapshots and deliberately do not refresh after every tool.

## Preserved limits and retention

| Behavior | 1.18.29 baseline | 2.1.4 migration |
|---|---|---|
| Large text shown inline |2,000 lines / 50 KiB default|Same native defaults; configurable `tool_output.max_lines/max_bytes`|
| Engine overflow-file retention |7 days|Same 7 days; upstream has no retention setting|
| Exact saved-output reader |4 KiB UTF-8 pages;1 MiB literal search per call|Same bounds, explicit continuation, no line-based loss|
| Saved-output ownership |Completed tool metadata, same-project parents;32-parent cutoff|Full native persisted-message pagination, same-directory parents, cycle detection; removed 32-parent cutoff|
| View generation preview |16 calls per request,200,000 characters per call,80 ms coalescing|Same preview bounds per assistant generation; native input events cover HTTP and WebSocket|
| Final view preview |Complete data retained in tool metadata|Complete metadata and structured output; preview-only limit does not shorten the final view|
| Live pane/workspace/folder cache |Office pane 5 s; workspace lookup 10 s; shallow project folders 15 s|Preserved; scoped to the invoking project/session|
| Domain input/output bounds |Existing service/Zod constraints|Preserved; structured conversion adds no new cap|

Code Mode adds upstream discovery/execution boundaries, separately from output
retention. Its inline catalog uses an approximate 2,000-token listing budget
and a 120-character first-line description preview. Every namespace remains
visible, and `search(...)` returns the full callable definitions when a listing
is omitted. Search defaults to ten results, accepts an explicit positive limit
without a fixed maximum, and returns `remaining`/`next.offset` for continuation;
these previews do not remove tools or shorten their results. This
is upstream's progressive-discovery mechanism, not a LegalWork tool-count cap.
The native runtime uses a confined JavaScript subset: imports, direct filesystem
access and timers are unavailable there; ordinary permitted shell/Python/script
tools remain available for full programs. The released Core creates that runtime
without an execution timeout, tool-call-count limit or result-byte budget, and
LegalWork adds none. Existing native output-file presentation still applies to
the outer result as documented above.

The retained exact-output reader is still needed: both engines can show zero lines for one long JSON line, while retaining the full text in an overflow file. It authenticates ownership through LegalWork's server using the full native message API, including messages before compaction. It then applies the existing explicit file-read permissions, regular-file/no-symlink checks and UTF-8 byte paging. An expired/deleted file is reported as unavailable; its text is not invented. Applications needing permanent evidence should save it through their domain's project-file/export tools.

## Provider corrections retained with evidence

Pinned 2.1.4 driver fixtures demonstrate three remaining compatibility cases:

- Anthropic's native driver still forwards top-level MCP `anyOf` schemas unchanged. The existing flattening correction now runs only on native Anthropic model requests; nested combinators and other providers retain their schema.
- Explicit legacy enabled-thinking options still become `enabled/budget_tokens` for Claude 5+. The existing narrow correction uses adaptive thinking and preserves explicit effort/output configuration. Already-native adaptive settings remain unchanged.
- Native OpenAI Responses still replays cross-provider tool IDs longer than 64 characters. Stable wire-only IDs now cover both native HTTP requests and Responses WebSocket frames. Original history and Gemini thought signatures remain intact.

There are no production global-fetch replacements. Live view generation uses native tool-input events instead of provider SSE sniffing. Provider corrections do not impose context/output caps, change model selection or touch stored provider-native replay data.

## Cancellation and verification boundaries

Native denial/cancellation propagates unchanged, including mandatory unsavable approval for project instructions and per-package skill/file grants. Existing HTTP budgets remain in place; no new task deadline is added. Undelivered Office writes are removed from the relay on cancellation and are not retried. An Office.js batch already delivered to an add-in cannot be rolled back; uncertain execution is reported and requires inspection before retrying.

Automated verification includes domain/routing/access regressions, provider-driver construction fixtures, exact byte paging, restart/revert/compaction reminders, Code Mode result contracts and isolated released-engine admission/restart checks. A released-engine Code Mode fixture consumes a complete 120,000-character structured result, returns its computed length, and verifies the resulting Office-state reminder is saved and included in the next model request. These fixtures use no paid model calls and do not establish real-model behavior quality or live Microsoft Office application parity. Those remain separate acceptance runs.

## Review inference workers

Background review cells now use a native worker-only submission tool instead of V1 `StructuredOutput`. Each in-flight attempt is bound to the actual project/session, selected model, server-owned column schema and document evidence. Only the trusted internal worker sees that exact schema and its narrow review instructions; unrelated app-pane state and general Office guidance are excluded. Ordinary chats cannot discover or invoke the submission tool. Successful submission is checked against the actual native assistant/tool identity, exact value schema, classification/yes-no requirements and strict source citations. Full output is retained.

The existing review request layer remains the sole correction/retry owner; the native worker retry hook cannot re-enable retries. Cancellation removes the in-flight claim and interrupts/deletes its worker. Claims are deliberately ephemeral: a server crash does not resume an unverified in-flight submission, while previously saved review answers remain intact and normal request recovery can rerun the unfinished cell. A released-engine HTTP model fixture verifies the actual advertised schema, selected transport, citation rejection/correction and clean worker teardown without paid inference.

The full [native browser integration contract](opencode-v2-browser.md) records the vendored upstream driver, shared-profile/network decisions, local/manual-server gateway, capability-preserving extensions and every material native/retained limit.
